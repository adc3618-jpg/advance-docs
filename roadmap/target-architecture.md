# 목표 아키텍처

> 범위: 프론트 / 스크래핑 서비스 / 잡서비스(API). 백오피스는 개선 대상 아님.

## 현재 아키텍처 요약

```
[사용자]
   │
   ▼
[프론트: JSP + Java 1.8 모놀리스] ──(내부 호출)── [잡서비스(API)]
   │                                                   │
   │                                                   ▼
   │                                            [폐쇄망 내부 DB]
   ▼
[세션 기반 인증]                              [스크래핑 서비스] ──(배치)── [외부 사이트 / 내부 DB]
```

- 온프레미스 + 폐쇄망(망분리) 환경에 3개 서비스(프론트, 스크래핑, 잡서비스)가 모두 위치.
- 프론트는 서버사이드 렌더링(JSP) + 세션 기반 인증의 모놀리식 구조.
- 배포 단위가 크고 무거워 CI/CD가 사실상 없는 상태 — 수동/저빈도 배포.
- 클라우드 자원(스토리지, 관측성, 오토스케일링 등)을 전혀 활용하지 못함.

## 목표 아키텍처

```
                        ┌───────────────────────────────────────────┐
                        │                  AWS                       │
                        │                                             │
 [사용자] ──HTTPS──▶ [CloudFront + S3 / Amplify]                     │
                        │   React SPA (정적 호스팅)                   │
                        │        │                                    │
                        │        ▼                                    │
                        │  [API Gateway / BFF]                        │
                        │        │                                    │
                        │        ▼                                    │
                        │  [DMZ VPC] ── Transit Gateway ── [내부망 VPC]│
                        │   (신규 API,                     (컨테이너화된│
                        │    DMZ API 계층)                  API/스크래핑)│
                        │        │                              │      │
                        └────────┼──────────────────────────────┼──────┘
                                 │      PrivateLink / Direct Connect
                                 │      (AWS Private Network)
                                 ▼                              ▼
                        ┌───────────────────────────────────────────┐
                        │        폐쇄망(On-premises, 망분리 구간)      │
                        │                                             │
                        │   [DMZ API] ──▶ [내부 DB]                   │
                        │   [기존 JSP → API화된 레거시 API]            │
                        └───────────────────────────────────────────┘

  CI/CD: GitHub Actions/CodePipeline → IaC(Terraform 등)로 위 인프라 전체를 코드로 관리
  관측성: CloudWatch + 구조화 로깅으로 프론트/게이트웨이/API 전 구간 추적
```

- **프론트**: React SPA로 전환, AWS(S3+CloudFront 또는 Amplify)에서 정적 호스팅. 장기적으로 마이크로프론트엔드 구조로 확장해 여러 서비스 화면을 하나의 슈퍼앱으로 묶는다.
- **API 계층**: 기존 JSP 로직은 폐기하지 않고 API로 감싸서 재사용(스트랭글러 무화과 패턴). 신규 기능은 처음부터 API로 개발.
- **DMZ API**: 폐쇄망 DB에 접근해야 하는 API는 DMZ 구간에 배치. 금융보안원 「금융분야 상용 클라우드서비스 보안 관리 참고서」가 제시하는 Multi-VPC(DMZ VPC/내부망 VPC + Transit Gateway) 패턴을 그대로 채택.
- **AWS Private Network (법규 확인 필요)**: 클라우드-폐쇄망 간 연결은 AWS PrivateLink 또는 Direct Connect로 구성해 인터넷 구간을 거치지 않는 것이 이상적이다. 다만 국내 법규상 PrivateLink/Direct Connect 자체가 어려울 가능성이 있어(확인 필요 — 법무팀 검토 필요), 이를 "확정 계획"이 아니라 **법무/컴플라이언스팀 검토가 선행되어야 하는 옵션 A**로 다룬다. 검토 결과에 따라 **옵션 B** — 퍼블릭 인터넷 구간을 쓰되 mTLS(상호 인증서)·IP 화이트리스트·WAF로 방어하는 DMZ API 노출, 또는 VPN 기반 연결 — 로 대체될 수 있다. 목표는 "인터넷 구간을 아예 안 거치는 것"이 아니라 "안전하게 거치는 것"으로 재정의될 수 있다.
- **스크래핑/잡서비스**: 컨테이너화(ECS/EKS 등)해 오토스케일링·스케줄링(EventBridge, Step Functions 등)의 이점을 받도록 이관.
- **인증**: JSP의 세션 기반 인증과 신규 API의 토큰 기반 인증(JWT/OAuth2)이 과도기에 공존한다. API Gateway 단에서 인증을 통합해 프론트 입장에서는 단일 인증 흐름으로 보이게 한다.

## 프론트엔드 렌더링 전략: SEO/GEO 고려

React SPA 전환 시 순수 CSR(Client-Side Rendering)만으로는 검색엔진 최적화(SEO)와 GEO(생성형 엔진 최적화 —
AI 검색/답변 엔진에 노출되기 위한 최적화) 양쪽에 불리하다. 크롤러가 초기 HTML만 보고 콘텐츠가 비어 있다고
판단하거나, 색인 시점과 실제 렌더링 결과가 어긋날 수 있기 때문이다. 지금은 KFESS가 단일 서비스로 운영되지만,
목표 5(장기 마이크로프론트엔드 슈퍼앱 확장)와 맞물려 여러 서비스/콘텐츠가 하나의 프론트로 모이면 이 콘텐츠를
사용자와 AI 검색 엔진 양쪽에 잘 노출시키는 것이 더 중요해진다.

- **렌더링 방식 선택지**:

  | 방식 | 설명 | SEO/GEO 영향 |
  | --- | --- | --- |
  | CSR (순수 SPA) | 브라우저가 JS 실행 후 콘텐츠를 렌더링 | 크롤러가 빈 HTML만 보는 경우가 있어 불리 |
  | SSR (Next.js 등) | 요청마다 서버가 완성된 HTML을 렌더링 | 크롤러/AI 크롤러가 완성된 콘텐츠를 바로 수집 — 가장 안전 |
  | SSG/ISR | 빌드 시점 또는 주기적으로 정적 HTML을 생성 | 콘텐츠 변경이 적은 페이지에 적합, 배포/호스팅 비용 최소화 |

  → React 전환 첫 단계부터 SSR 또는 SSG/ISR을 프론트엔드 기술 선택(Next.js 등)에 포함해 검토한다.
  CSR 단독 SPA는 지양한다.
- **구조화 데이터/시맨틱 마크업**: JSON-LD 등 구조화 데이터와 시맨틱 HTML 태그를 사용해 검색엔진·AI 크롤러가
  콘텐츠 의미를 파악하기 쉽게 한다.
- **AI 크롤러 대응**: `llms.txt`류 관행 등 AI 크롤러를 위한 실무 관행도 조사해 반영한다.
- **URL 설계 — 의미 있는 슬러그(slug)**: 숫자 ID 기반 URL 대신 콘텐츠를 설명하는 슬러그를 쓴다. 검색엔진과
  생성형 엔진 모두 URL 자체를 콘텐츠 신호로 사용한다.
  - 예) `.../kfess/notice/1` (X) → `.../kfess/notice/2026-fx-rate-change-notice` (O)
  - 신규 API/React 라우팅 설계 시점부터 사람이 읽어도 내용을 짐작할 수 있는 슬러그 기반 경로로 정한다.
  - 기존 JSP 화면에 숫자 ID 기반 URL이 있다면 React 전환 시 슬러그 기반 URL로 정리하고, 기존 ID URL은
    **301 리다이렉트**로 연결해 기존 색인/링크의 SEO 가치를 보존한다.

## 점진적 전환을 앞당기는 방법: CDN 리버스 프록시

현재 가장 큰 제약은 "도메인이 클라우드 환경에 있지 않아 경로 기반 라우팅이 불가능"하다는 점이다 — 이 때문에 페이지 단위 점진 전환(스트랭글러 무화과 패턴)이 2단계(도메인/인프라 이관) 이후로 미뤄져 있었다. 하지만 도메인 소유권을 완전히 옮기지 않고도 이 제약을 먼저 풀 수 있는 방법이 있다.

- **아이디어**: `flow.kgfinancial.co.kr`의 DNS를 CloudFront로 향하게 하고, CloudFront의 오리진으로 기존 온프레미스 서버(커스텀 오리진)를 그대로 등록한다. 이후 신규로 만든 경로(예: `/kfess/react/*`, `/api/*`)만 S3(React 정적 자산)나 API Gateway로 라우팅하고, 나머지 경로는 지금처럼 온프레미스 JSP 모놀리스로 그대로 전달한다.
- **효과**: 인프라 전체를 클라우드로 옮기지 않고도 CloudFront의 경로 기반 캐시 동작(behavior) 설정만으로 페이지 단위 점진 전환이 즉시 가능해진다 — 즉 목표 아키텍처의 2단계에 있던 작업 일부를 1.5단계로 앞당길 수 있다.
- **전제조건**: CloudFront → 온프레미스 오리진 구간은 새로 뚫는 것이 아니라, DMZ API 구축과 함께 마련하는 폐쇄망 연결 경로(퍼블릭 엔드포인트 또는 PrivateLink)를 재사용한다. TLS 인증서와 DNS 컷오버는 별도 작업으로 선행되어야 한다.
- **근거**: 참고 자료의 "Strangler fig pattern — AWS Prescriptive Guidance"가 제시하는 대표 구현 방식 중 하나가 바로 CDN/리버스 프록시를 오리진 앞단에 두고 경로별로 신구 시스템을 분기하는 것이다.
- **오리진 설정 시 주의 — IP가 아니라 도메인**: CloudFront의 커스텀 오리진을 온프레미스 레거시 서버의 **IP로 직접** 등록하는 방식은 권장하지 않는다.
  - 오리진 서버 인증서가 보통 도메인 이름 기준으로 발급되어 있어, IP 직결 시 TLS 검증이 깨질 수 있다.
  - 서버 교체·장애조치 등으로 IP가 바뀔 때마다 CloudFront 배포 설정을 매번 손대야 한다.
  - 사내망 사설 IP는 CloudFront가 애초에 도달할 수 없다 — 퍼블릭 노출 엔드포인트나 VPC 오리진이 필요하다.
  - 대신 CloudFront는 **DMZ VPC 쪽 게이트웨이(ALB/NLB 등)의 도메인**을 오리진으로 잡고, 그 게이트웨이가 위 "AWS Private Network" 절의 옵션 A(PrivateLink/Direct Connect) 또는 옵션 B(mTLS·IP 화이트리스트 기반 퍼블릭 엔드포인트)로 사내망 레거시 서버에 연결하는 구조를 취한다.

```
[사용자]
   │ HTTPS
   ▼
[CloudFront] ── 오리진 도메인: flow.kgfinancial.co.kr (IP 직결 금지)
   │
   ├──(신규 경로: /kfess/react/*, /api/*)──▶ [S3: React 정적 자산] / [API Gateway]
   │
   └──(그 외 기존 경로 전부)──▶ [DMZ VPC 게이트웨이(ALB/NLB, 도메인)]
                                         │
                                         │ 옵션 A: PrivateLink/Direct Connect
                                         │ 옵션 B: mTLS + IP 화이트리스트(퍼블릭)
                                         ▼
                                  [사내망 레거시 JSP 서버]
```

## 마이그레이션 단계

1. **API 우선 구축 (현재 단계)** — 모놀리식은 유지한 채 신규 API를 추가하고, 기존 JSP 프론트는 vanilla JS로 이 API들과 연동. 이 단계의 API 서비스부터 CI/CD를 우선 구축한다.
2. **인증/세션 정리** — 세션 기반 인증과 신규 API 인증 방식을 정리해, 이후 단계에서 프론트를 옮겨도 인증이 끊기지 않도록 설계한다.
3. **DMZ API 설계·구축** — 폐쇄망 DB 접근을 API로 추상화. 금융보안원 Multi-VPC(DMZ/내부망 + Transit Gateway) 패턴을 참고해 구성.
4. **클라우드-폐쇄망 연결 방식 확정 (옵션 A/B)** — 법무/컴플라이언스팀 검토 결과에 따라 AWS PrivateLink/Direct Connect(옵션 A) 또는 mTLS·IP 화이트리스트·WAF 기반 퍼블릭 엔드포인트/VPN(옵션 B)으로 클라우드와 폐쇄망을 연결.
5. **관측성/IaC 기반 마련** — 이후 단계의 잦은 배포·인프라 변경을 안전하게 반복하기 위한 선행 작업.
6. **도메인/인프라 클라우드 이관** — 도메인을 AWS로 옮겨 경로 기반 라우팅 등 클라우드 네이티브 구성이 가능해지도록 준비.
7. **React 전환** — 클라우드로 옮긴 도메인 위에서 프론트엔드를 React SPA로 전환. CI/CD를 프론트에도 확장.
8. **스크래핑/잡서비스 컨테이너화 및 이관** — 배치성 워크로드를 이벤트 기반 스케줄링으로 전환.
9. **(장기) 마이크로프론트엔드/슈퍼앱 확장** — 여러 마이크로서비스 화면을 하나의 프론트 셸로 통합.

## 리스크 및 고려사항

- 모놀리식과 신규 API가 공존하는 기간의 병행 운영 부담 (배포·장애 대응 이중화).
- 기존 JSP(세션 기반 인증)와 vanilla JS로 호출하는 신규 API 간 인증/세션 처리 방식을 먼저 정리해야, 이후 React 전환 시 인증을 다시 설계하지 않아도 된다.
- 점진적 페이지 단위 전환이 어려움 — 도메인이 클라우드 환경에 있지 않아 경로 기반 라우팅 구성이 현재는 불가능. **대응**: 위 "CDN 리버스 프록시" 방식으로 도메인 완전 이관 전에도 경로 기반 라우팅을 선제적으로 확보할 수 있다.
- 금융 데이터 특성상 DMZ API와 Private Network 구간의 보안 검토(제로트러스트, 접근 통제)가 일정에 선행되어야 한다.
- PrivateLink/Direct Connect 등 AWS Private Network 연결이 국내 법규상 어려울 가능성이 있음(확인 필요 — 법무팀 검토 필요). 이 경우를 대비해 대안(옵션 B: mTLS/IP 화이트리스트/WAF 기반 퍼블릭 엔드포인트, VPN 등)으로 전환할 준비를 함께 갖춰야 한다.
