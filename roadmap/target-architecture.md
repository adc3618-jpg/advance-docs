# 목표 아키텍처

> 범위: 프론트 / 스크래핑 서비스 / 잡서비스(API).

## 현재 아키텍처 요약

```
[사용자]
   │
   ▼
[프론트: JSP + Java 1.8 모놀리스] ──(내부 호출)── [잡서비스(API)]
   │                                                   │
   │                                                   ▼
   │                                            [폐쇄망 내부 DB]
   ▼
[세션 기반 인증]                              [스크래핑 서비스] ──(배치)── [외부 사이트 / 내부 DB]
```

- 온프레미스 + 폐쇄망(망분리) 환경에 3개 서비스(프론트, 스크래핑, 잡서비스)가 모두 위치.
- 프론트는 서버사이드 렌더링(JSP) + 세션 기반 인증의 모놀리식 구조.
- 배포 단위가 크고 무거워 CI/CD가 사실상 없는 상태 — 수동/저빈도 배포.
- 클라우드 자원(스토리지, 관측성, 오토스케일링 등)을 전혀 활용하지 못함.

## 목표 아키텍처

```
                        ┌───────────────────────────────────────────┐
                        │                  AWS                       │
                        │                                             │
 [사용자] ──HTTPS──▶ [CloudFront] ──▶ [ALB] ──▶ [ECS(Fargate)]       │
                        │   정적 자산은 S3      Next.js 컨테이너      │
                        │   캐싱                (SSR/SSG)             │
                        │        │                                    │
                        │        ▼                                    │
                        │  [API Gateway / BFF]                        │
                        │        │                                    │
                        │        ▼                                    │
                        │  [DMZ VPC] ── Transit Gateway ── [내부망 VPC]│
                        │   (신규 API,                     (컨테이너화된│
                        │    DMZ API 계층)                  API/스크래핑)│
                        │        │                              │      │
                        └────────┼──────────────────────────────┼──────┘
                                 │      PrivateLink / Direct Connect
                                 │      (AWS Private Network)
                                 ▼                              ▼
                        ┌───────────────────────────────────────────┐
                        │        폐쇄망(On-premises, 망분리 구간)      │
                        │                                             │
                        │   [DMZ API] ──▶ [내부 DB]                   │
                        │   [기존 JSP → API화된 레거시 API]            │
                        └───────────────────────────────────────────┘

  CI/CD: GitHub Actions/CodePipeline → IaC(Terraform 등)로 위 인프라 전체를 코드로 관리
  관측성: CloudWatch + 구조화 로깅으로 프론트/게이트웨이/API 전 구간 추적
```

- **프론트**: **Next.js**로 전환해 **ECS(Fargate) 컨테이너**로 배포한다. 앞단에 CloudFront를 두어 정적 자산(`_next/static` 등)은 CDN에서 캐싱하고, 렌더링이 필요한 요청만 ALB를 거쳐 ECS로 보낸다. JSP가 하던 서버사이드 렌더링을 Next.js가 이어받으므로 SEO·초기 렌더링 성능을 잃지 않고, 인증 토큰이나 내부 API 주소를 브라우저에 노출하지 않고 서버 측(Route Handler/서버 컴포넌트)에서 처리할 수 있어 DMZ API 구조와도 잘 맞는다. 장기적으로 마이크로프론트엔드 구조로 확장해 여러 서비스 화면을 하나의 슈퍼앱으로 묶는다.
- **API 계층**: 기존 JSP 로직은 폐기하지 않고 API로 감싸서 재사용(스트랭글러 무화과 패턴). 신규 기능은 처음부터 API로 개발.
- **DMZ API**: 폐쇄망 DB에 접근해야 하는 API는 DMZ 구간에 배치. 금융보안원 「금융분야 상용 클라우드서비스 보안 관리 참고서」가 제시하는 Multi-VPC(DMZ VPC/내부망 VPC + Transit Gateway) 패턴을 그대로 채택.
- **AWS Private Network (법규 확인 필요)**: 클라우드-폐쇄망 간 연결은 AWS PrivateLink 또는 Direct Connect로 구성해 인터넷 구간을 거치지 않는 것이 이상적이다. 다만 국내 법규상 PrivateLink/Direct Connect 자체가 어려울 가능성이 있어(확인 필요 — 법무팀 검토 필요), 이를 "확정 계획"이 아니라 **법무/컴플라이언스팀 검토가 선행되어야 하는 옵션 A**로 다룬다. 검토 결과에 따라 **옵션 B** — 퍼블릭 인터넷 구간을 쓰되 mTLS(상호 인증서)·IP 화이트리스트·WAF로 방어하는 DMZ API 노출, 또는 VPN 기반 연결 — 로 대체될 수 있다. 목표는 "인터넷 구간을 아예 안 거치는 것"이 아니라 "안전하게 거치는 것"으로 재정의될 수 있다.
- **스크래핑/잡서비스**: 컨테이너화(ECS/EKS 등)해 오토스케일링·스케줄링(EventBridge, Step Functions 등)의 이점을 받도록 이관.
- **인증**: JSP의 세션 기반 인증과 신규 API의 토큰 기반 인증(JWT/OAuth2)이 과도기에 공존한다. API Gateway 단에서 인증을 통합해 프론트 입장에서는 단일 인증 흐름으로 보이게 한다 — 구체적인 브릿지 방식은 아래 "인증 전환 상세" 절 참고.

## 변경점과 이유

| 변경 항목 | 현재 | 목표 | 이유 |
| --- | --- | --- | --- |
| 프론트엔드 렌더링 | JSP 서버사이드 렌더링 | Next.js (SSR/SSG 선택) | 서버사이드 렌더링의 SEO·초기 렌더링 이점을 유지한 채 프론트 생태계로 이동 |
| 프론트엔드 언어/런타임 | Java 1.8 | Node/Next.js (프론트) + API는 Java 11 → 17(LTS)로 단계적 업그레이드 | 최신 보안 패치, 채용 시장, 라이브러리 생태계 |
| 프론트엔드 호스팅 | 온프레미스 | AWS ECS(Fargate) 컨테이너 + 앞단 CloudFront | 배포 속도, 오토스케일, 다른 서비스와 동일한 배포·운영 방식 |
| 기존 JSP 로직 | 화면과 로직이 결합 | API로 추출해 재사용 | 재작성 리스크·비용 최소화 (스트랭글러 패턴) |
| 배포 | 수동/저빈도, 모놀리식 단위 | CI/CD 자동화, 서비스 단위 | 신규 기능을 빠르게 배포해야 하는 요구 충족 |
| 인프라 구성 | 수기/문서 기반 | IaC(Terraform 등) | 재현성, 리뷰 가능한 인프라 변경, 재해복구 |
| 폐쇄망 DB 접근 | 내부망 안에서만 직접 접근 | DMZ API 경유 | 클라우드로 옮긴 화면/서비스가 안전하게 참조 가능 |
| 클라우드-온프레미스 연결 | 없음(완전 분리) | AWS PrivateLink/Direct Connect | 인터넷 구간 노출 없이 폐쇄망 자원 접근 |
| 인증 | 세션 기반(JSP) | 토큰 기반(JWT/OAuth2) + Gateway 통합 | 웹/모바일/여러 서비스가 공유 가능한 인증 체계 |
| 스크래핑/배치 잡 | 온프레미스 상시 프로세스 | 컨테이너 + 이벤트 기반 스케줄링 | 리소스 사용에 맞춘 과금, 운영 부담 감소 |
| 관측성 | 서버 로그 파일 위주 | 구조화 로깅 + CloudWatch/APM | 장애 원인 추적 시간 단축, 배포 빈도 증가에 대응 |
| 자격증명 관리 | 설정 파일(properties)·소스에 평문 저장 또는 서버에 직접 배치 | AWS Secrets Manager/Parameter Store + IAM 역할 기반 런타임 주입 | 소스·이미지 유출 시에도 자격증명 노출 방지, 로테이션 자동화 |
| 프론트 구조(장기) | 단일 모놀리식 프론트 | 마이크로프론트엔드(슈퍼앱) | 여러 서비스 화면을 독립 배포하면서 하나의 UX로 통합 |

## 왜 Next.js인가

React를 그대로 CSR(Client-Side Rendering) SPA로 쓰지 않고 Next.js를 선택한 핵심 이유는 SEO다.

| Next.js의 장점 | 지금 우리 상황에서 의미하는 것 |
| --- | --- |
| **SSR이 CSR보다 SEO에 유리** | CSR SPA는 브라우저가 JS를 실행해야 콘텐츠가 채워지므로, 크롤러가 초기 HTML만 보고 콘텐츠가 비어 있다고 판단할 수 있다. Next.js는 서버사이드 렌더링을 기본으로 지원해, JSP가 갖고 있던 SEO 이점을 그대로 이어받으면서 프론트 생태계만 현대화할 수 있다. |

**대가도 있다.** 어떤 화면·컴포넌트를 서버에서 렌더링(SSR)하고 어떤 것을 브라우저에서 렌더링(CSR)할지 명확히 나눠서 설계·개발해야 한다. 이 경계를 신경 쓰지 않고 아무 컴포넌트나 클라이언트 컴포넌트로 짜면 실질적으로 CSR SPA가 되어버려 Next.js를 도입한 의미(SEO 이점)가 사라진다. 즉 순수 CSR 하나만 개발하던 것과 비교하면 **개발 복잡도가 올라간다** — 이 구분을 코드 리뷰·컨벤션으로 지속적으로 지켜야 한다.

### CSR vs SSR 비교

위 "SEO에 유리하다 / 개발 복잡도가 올라간다"는 결론의 근거를 항목별로 나누면 다음과 같다. Next.js를 쓰더라도 화면마다 SSR/SSG로 갈지 클라이언트 컴포넌트(CSR)로 갈지 판단할 때 이 표를 기준으로 삼는다.

| 항목 | CSR (순수 SPA / 클라이언트 컴포넌트) | SSR (Next.js 서버 컴포넌트·기본 동작) |
| --- | --- | --- |
| **SEO / 초기 렌더링** | 브라우저가 JS를 실행해야 콘텐츠가 채워짐 — 크롤러가 빈 HTML만 보고 색인 실패 가능 | 요청 시점에 서버가 완성된 HTML을 내려줌 — 크롤러/AI 크롤러가 완성된 콘텐츠를 바로 수집 |
| **서버 부하 / 인프라 비용** | 정적 파일만 서빙하면 되므로 S3+CloudFront 같은 정적 호스팅으로 충분, 요청당 서버 연산 없음 | 요청마다 서버가 렌더링을 수행해야 해 ECS(Fargate) 같은 상시 실행 서버가 필요 — 트래픽에 비례해 컴퓨팅 비용 발생 (SSG/ISR로 빌드 시점에 미리 렌더링해두면 이 비용을 줄일 수 있음) |
| **초기 로딩 속도 vs 페이지 전환 속도** | 첫 로딩 시 JS 번들을 모두 받고 실행할 때까지 빈 화면(또는 스켈레톤) — 느림. 이후 라우팅은 클라이언트에서 처리해 페이지 전환이 매우 빠름(SPA 특유의 체감) | 첫 로딩은 서버가 완성된 HTML을 바로 내려줘 콘텐츠가 빠르게 보임. 다만 페이지 전환마다 서버 왕복(또는 하이드레이션)이 끼어들 수 있어 SPA만큼의 전환 체감 속도는 별도로 신경 써야 함(Next.js의 클라이언트 사이드 라우팅·프리페치로 완화) |
| **개발/디버깅 복잡도** | 렌더링 환경이 브라우저 하나뿐이라 상대적으로 단순 — `window`, `localStorage` 등 브라우저 API를 자유롭게 사용 | 같은 컴포넌트가 서버(Node.js)와 브라우저 양쪽에서 실행될 수 있어, 서버·클라이언트 렌더링 결과가 어긋나는 **하이드레이션(hydration) 불일치** 같은 Next.js 고유의 버그 클래스가 생긴다. 브라우저 전용 API는 클라이언트 컴포넌트로 격리해야 하는 등 컴포넌트 경계 설계 자체가 새로운 학습 비용 |
| **캐싱 전략** | 정적 자산(JS/CSS 번들) 단위로 CDN에 오래 캐싱 — 콘텐츠 갱신은 새 번들 배포로만 반영 | 페이지/데이터 단위로 캐싱 정책을 나눠 가져갈 수 있음 — 변경이 거의 없는 화면은 SSG/ISR로 CDN에 캐싱하고, 실시간성이 필요한 화면만 매 요청 SSR로 처리하는 식으로 화면별 세밀한 제어 가능 (그만큼 캐시 무효화 전략을 화면마다 설계해야 하는 부담도 있음) |

→ 결론은 동일하다: SEO/GEO 이점 때문에 SSR을 기본으로 채택하되, 변경이 적은 화면은 SSG/ISR로 서버 부하와 비용을 낮추고, 인터랙션 위주 화면(관리 폼, 대시보드 등)은 의도적으로 클라이언트 컴포넌트(CSR)로 남겨 개발 복잡도를 필요한 곳에만 쓴다.

## 왜 컨테이너(ECS)인가

프론트(Next.js)·신규 API·스크래핑/잡서비스를 모두 컨테이너 이미지로 만들어 ECS에 올린다. 정적 호스팅(S3+CloudFront)이나 서버에 직접 배포하는 방식 대신 컨테이너를 택하는 이유는 다음과 같다.

| 컨테이너의 장점 | 지금 우리 상황에서 의미하는 것 |
| --- | --- |
| **환경 동일성** | 런타임·라이브러리·설정이 이미지 안에 함께 담긴다. 지금은 서버에 설치된 Java 1.8과 톰캣 설정에 배포가 묶여 있어 "그 서버에서만 되는" 상태지만, 이미지로 고정하면 로컬·스테이징·운영이 같은 것을 실행한다. |
| **배포 = 이미지 교체** | 배포 단위가 "빌드 산출물 + 서버 상태"가 아니라 이미지 하나로 좁혀진다. 롤백도 이전 이미지 태그로 되돌리면 끝이라, 지금처럼 배포가 무겁고 되돌리기 어려운 문제의 직접적인 해법이 된다. |
| **CI/CD와 자연스럽게 연결** | 빌드 → ECR 푸시 → ECS 서비스 업데이트가 그대로 파이프라인이 된다. ECS의 롤링 업데이트(또는 CodeDeploy 블루/그린)로 무중단 배포와 자동 롤백을 표준으로 쓸 수 있다. |
| **오토스케일링** | 트래픽에 따라 태스크 수를 늘리고 줄인다. 온프레미스처럼 피크에 맞춘 서버를 상시 띄워둘 필요가 없다. |
| **서버 관리 부담 감소** | Fargate를 쓰면 EC2 인스턴스·OS 패치·AMI 관리가 사라진다. 인프라 인력이 얇은 상황에서 특히 크다. |
| **리소스 격리** | 스크래핑 배치가 튀어도 프론트/API 자원을 잠식하지 않는다. 지금은 같은 서버 자원을 나눠 쓰는 구조라 서로 영향을 준다. |
| **런타임 업그레이드 실험이 안전해짐** | Java 11 → 17 같은 업그레이드를 이미지 태그만 바꿔 일부 태스크에만 먼저 태워보고(카나리), 문제가 있으면 즉시 되돌릴 수 있다. |
| **이식성** | 같은 이미지를 클라우드와 폐쇄망 양쪽에서 실행할 수 있다. DMZ API처럼 위치가 바뀔 수 있는 구성 요소를 옮길 때 재작업이 줄어든다. |

**대가도 분명하다.** 이미지 빌드·레지스트리·오케스트레이션이라는 학습 비용이 새로 생기고, Next.js를 정적 호스팅이 아니라 ECS에서 상시 실행하면 정적 배포보다 운영 부담과 비용이 올라간다. 그럼에도 컨테이너를 택하는 이유는, 어차피 스크래핑/잡서비스는 컨테이너화가 필요하고 프론트만 다른 방식으로 배포하면 CI/CD·관측성·롤백 절차를 두 벌로 유지해야 하기 때문이다. 배포 방식을 하나로 통일하는 값이 개별 최적화보다 크다고 본다.

> 정적 자산까지 ECS로 서빙하지는 않는다. `_next/static` 같은 자산은 CloudFront(필요하면 S3 오리진)에서 캐싱하고, ECS는 렌더링이 필요한 요청만 처리한다.

## 프론트엔드 렌더링 전략: SEO/GEO 고려

프론트엔드를 순수 CSR(Client-Side Rendering) SPA로 만들었다면 검색엔진 최적화(SEO)와 GEO(생성형 엔진 최적화 —
AI 검색/답변 엔진에 노출되기 위한 최적화) 양쪽에 불리했을 것이다. 크롤러가 초기 HTML만 보고 콘텐츠가 비어 있다고
판단하거나, 색인 시점과 실제 렌더링 결과가 어긋날 수 있기 때문이다. **Next.js를 선택한 이유 중 하나가 바로 이
문제를 프레임워크 차원에서 해결한다는 점이다** — JSP가 하던 서버사이드 렌더링을 SSR/SSG로 그대로 이어받아,
별도로 SSR 전용 프레임워크를 다시 검토할 필요가 없다. 지금은 KFESS가 단일 서비스로 운영되지만, 목표 5(장기
마이크로프론트엔드 슈퍼앱 확장)와 맞물려 여러 서비스/콘텐츠가 하나의 프론트로 모이면 이 콘텐츠를 사용자와
AI 검색 엔진 양쪽에 잘 노출시키는 것이 더 중요해진다.

- **페이지별 렌더링 방식 선택**:

  | 방식 | 설명 | SEO/GEO 영향 |
  | --- | --- | --- |
  | CSR (순수 SPA) | 브라우저가 JS 실행 후 콘텐츠를 렌더링 | 크롤러가 빈 HTML만 보는 경우가 있어 불리 — Next.js에서도 클라이언트 컴포넌트만으로 짠 화면은 이 함정에 그대로 빠진다 |
  | SSR (Next.js 서버 컴포넌트/기본 동작) | 요청마다 서버가 완성된 HTML을 렌더링 | 크롤러/AI 크롤러가 완성된 콘텐츠를 바로 수집 — 가장 안전, 자주 바뀌는 화면(공지사항 상세 등)에 적합 |
  | SSG/ISR (Next.js `generateStaticParams`/재검증) | 빌드 시점 또는 주기적으로 정적 HTML을 생성 | 콘텐츠 변경이 적은 페이지(약관, 소개 등)에 적합, ECS 부하와 호스팅 비용 최소화 |

  → 화면마다 변경 빈도를 기준으로 SSR/SSG를 선택한다. 인터랙션 위주가 아닌 화면을 클라이언트 컴포넌트로만
  짜서 실질적인 CSR SPA가 되어버리는 것을 코드 리뷰에서 걸러낸다.
- **구조화 데이터/시맨틱 마크업**: JSON-LD 등 구조화 데이터와 시맨틱 HTML 태그를 사용해 검색엔진·AI 크롤러가
  콘텐츠 의미를 파악하기 쉽게 한다.
- **AI 크롤러 대응**: `llms.txt`류 관행 등 AI 크롤러를 위한 실무 관행도 조사해 반영한다.
- **URL 설계 — 의미 있는 슬러그(slug)**: 숫자 ID 기반 URL 대신 콘텐츠를 설명하는 슬러그를 쓴다. 검색엔진과
  생성형 엔진 모두 URL 자체를 콘텐츠 신호로 사용한다.
  - 예) `.../kfess/notice/1` (X) → `.../kfess/notice/2026-fx-rate-change-notice` (O)
  - 신규 API/Next.js 라우팅 설계 시점부터 사람이 읽어도 내용을 짐작할 수 있는 슬러그 기반 경로로 정한다.
  - 기존 JSP 화면에 숫자 ID 기반 URL이 있다면 Next.js 전환 시 슬러그 기반 URL로 정리하고, 기존 ID URL은
    **301 리다이렉트**(Next.js `redirects()` 설정)로 연결해 기존 색인/링크의 SEO 가치를 보존한다.

## 참고: 무조건 잘게 쪼개는 것이 정답은 아니다

Amazon Prime Video 팀은 영상 품질 분석 파이프라인을 마이크로서비스에서 단일 프로세스로 되돌려 인프라 비용을 90% 절감한 사례가 있다. 서비스 경계를 나누는 목적은 "작게 쪼개는 것" 자체가 아니라 "독립적으로 배포·확장해야 할 이유가 있는 경계를 찾는 것"이다. 우리 아키텍처에서도 각 서비스(프론트/스크래핑/잡서비스) 및 향후 마이크로프론트엔드 분리는 실제 배포 주기·트래픽 패턴 차이가 있는 경계인지 먼저 검증한 뒤 나눈다.

## 점진적 전환을 앞당기는 방법: CDN 리버스 프록시

현재 가장 큰 제약은 "도메인이 클라우드 환경에 있지 않아 경로 기반 라우팅이 불가능"하다는 점이다 — 이 때문에 페이지 단위 점진 전환(스트랭글러 무화과 패턴)이 2단계(도메인/인프라 이관) 이후로 미뤄져 있었다. 하지만 도메인 소유권을 완전히 옮기지 않고도 이 제약을 먼저 풀 수 있는 방법이 있다.

- **아이디어**: `flow.kgfinancial.co.kr`의 DNS를 CloudFront로 향하게 하고, CloudFront의 오리진으로 기존 온프레미스 서버(커스텀 오리진)를 그대로 등록한다. 이후 신규로 만든 경로(예: `/kfess/next/*`, `/api/*`)만 ALB(Next.js ECS 서비스)나 API Gateway로 라우팅하고, 나머지 경로는 지금처럼 온프레미스 JSP 모놀리스로 그대로 전달한다.
- **효과**: 인프라 전체를 클라우드로 옮기지 않고도 CloudFront의 경로 기반 캐시 동작(behavior) 설정만으로 페이지 단위 점진 전환이 즉시 가능해진다 — 즉 목표 아키텍처의 2단계에 있던 작업 일부를 1.5단계로 앞당길 수 있다.
- **전제조건**: CloudFront → 온프레미스 오리진 구간은 새로 뚫는 것이 아니라, DMZ API 구축과 함께 마련하는 폐쇄망 연결 경로(퍼블릭 엔드포인트 또는 PrivateLink)를 재사용한다. TLS 인증서와 DNS 컷오버는 별도 작업으로 선행되어야 한다.
- **근거**: 참고 자료의 "Strangler fig pattern — AWS Prescriptive Guidance"가 제시하는 대표 구현 방식 중 하나가 바로 CDN/리버스 프록시를 오리진 앞단에 두고 경로별로 신구 시스템을 분기하는 것이다.
- **오리진 설정 시 주의 — IP가 아니라 도메인**: CloudFront의 커스텀 오리진을 온프레미스 레거시 서버의 **IP로 직접** 등록하는 방식은 권장하지 않는다.
  - 오리진 서버 인증서가 보통 도메인 이름 기준으로 발급되어 있어, IP 직결 시 TLS 검증이 깨질 수 있다.
  - 서버 교체·장애조치 등으로 IP가 바뀔 때마다 CloudFront 배포 설정을 매번 손대야 한다.
  - 사내망 사설 IP는 CloudFront가 애초에 도달할 수 없다 — 퍼블릭 노출 엔드포인트나 VPC 오리진이 필요하다.
  - 대신 CloudFront는 **DMZ VPC 쪽 게이트웨이(ALB/NLB 등)의 도메인**을 오리진으로 잡고, 그 게이트웨이가 위 "AWS Private Network" 절의 옵션 A(PrivateLink/Direct Connect) 또는 옵션 B(mTLS·IP 화이트리스트 기반 퍼블릭 엔드포인트)로 사내망 레거시 서버에 연결하는 구조를 취한다.

```
[사용자]
   │ HTTPS
   ▼
[CloudFront] ── 오리진 도메인: flow.kgfinancial.co.kr (IP 직결 금지)
   │
   ├──(신규 경로: /kfess/next/*, /api/*)──▶ [ALB → ECS: Next.js] / [API Gateway]
   │
   └──(그 외 기존 경로 전부)──▶ [DMZ VPC 게이트웨이(ALB/NLB, 도메인)]
                                         │
                                         │ 옵션 A: PrivateLink/Direct Connect
                                         │ 옵션 B: mTLS + IP 화이트리스트(퍼블릭)
                                         ▼
                                  [사내망 레거시 JSP 서버]
```

## CDN 라우팅을 보완하는 점진적 노출: Feature Flag

위 CDN 리버스 프록시는 **경로(path) 단위**로 신구 시스템을 나눈다 — 어떤 URL 패턴은 무조건 Next.js로, 나머지는 무조건 레거시 JSP로 가는 전부-아니면-전무(all-or-nothing) 방식이다. 같은 경로 안에서 **사용자 비율/세그먼트 단위**로 더 세밀하게 신규 화면을 노출하려면(예: 내부 직원에게만 먼저 열어보기, 신규 가입자부터 5%씩 확대) CDN 라우팅만으로는 부족하다 — 이 지점에서 feature flag가 CDN 라우팅과 역할을 나눠 맡는다.

- **역할 분담**: CDN(경로 라우팅)은 "이 URL 패턴 자체가 신규 시스템 소관인가"를 정하고, feature flag는 "그 안에서 지금 이 사용자에게 신규 화면을 보여줄 것인가"를 정한다. 두 단계가 함께 있어야 경로 단위로는 이미 Next.js로 넘어온 페이지 안에서도 안전하게 점진 확대·즉시 롤백이 가능하다.
- **패턴**: interception layer(BFF 또는 Next.js 미들웨어)가 요청마다 flag 값을 확인해 신규 로직/화면과 기존 로직 중 하나로 분기한다. 라우팅 로직 자체는 코드 배포 없이 flag 설정 변경만으로 트래픽 비율을 5% → 50% → 100%로 조정하거나, 문제 발생 시 즉시 0%로 되돌릴 수 있다.
- **AWS 선택지**: 이미 AWS를 표준으로 쓰기로 한 만큼, [AWS AppConfig](https://aws.amazon.com/about-aws/whats-new/2022/03/aws-appconfig-feature-flags)(Systems Manager의 기능)의 Feature Flags를 우선 검토한다. [2024년 추가된 타겟/변형/분할(targets, variants, splits) 기능](https://aws.amazon.com/about-aws/whats-new/2024/07/aws-appconfig-feature-flag-targets-variants-splits)으로 사용자 세그먼트별 다른 값을 배분할 수 있고, CloudWatch 알람과 연동한 자동 롤백 가드레일도 기본 제공한다. 별도 SaaS(Unleash 등) 도입 없이 기존 AWS 계정 안에서 운영 가능하다는 점이 우리 상황에 맞는다.
- **CI/CD 파이프라인과의 관계**: 위 "CI/CD 파이프라인 설계"의 카나리(인프라 단위 — 일부 ECS 태스크에 새 이미지)와 feature flag(요청 단위 — 사용자 비율)는 서로 다른 층이다. 이미지 배포 자체는 카나리로 안전하게 확대하고, 그 안에서 어떤 사용자에게 신규 코드 경로를 노출할지는 flag로 별도 제어한다 — 배포와 노출을 분리하면 "배포했지만 아직 아무에게도 안 보여준 상태"가 가능해져 리스크가 더 줄어든다.

## 인증 전환 상세: 세션 → 토큰, 과도기 브릿지

지금까지 "인증"은 목표 아키텍처 요약과 아래 마이그레이션 단계 2("인증/세션 정리")에서 "정리가 필요하다"는 목표로만 언급되고, 구체적으로 어떻게 정리할지는 다뤄지지 않았다. 특히 위 "CDN 리버스 프록시" 절을 도입하면 이 문제가 바로 현실이 된다 — 같은 도메인(`flow.kgfinancial.co.kr`) 아래에서 어떤 경로는 레거시 JSP(세션 쿠키 기반 인증)로, 어떤 경로는 신규 Next.js/API(토큰 기반 인증)로 갈리지만, 사용자 입장에서는 로그인 한 번으로 양쪽 다 접근되는 하나의 세션처럼 느껴져야 한다.

- **브릿지 계층**: 로그인 자체는 과도기 동안 계속 기존 JSP 로그인 화면/로직이 처리한다(세션 생성, `JSESSIONID` 쿠키 발급 — 로그인 로직 자체를 다시 만드는 리스크를 피한다). 여기에 API Gateway/BFF 계층에 **토큰 교환(token exchange) 엔드포인트**를 추가해, 유효한 레거시 세션을 검증한 뒤 신규 API가 쓸 단명(short-lived) JWT로 바꿔준다. 신규 API/Next.js는 이 JWT만 검증하면 되고 레거시 세션 스토어를 직접 알 필요가 없다.
  - 이 패턴은 새로 발명하는 것이 아니라 [RFC 8693(OAuth 2.0 Token Exchange)](https://www.rfc-editor.org/info/rfc8693/)이 표준화한 문제의 다른 형태다 — RFC 8693은 원래 SAML처럼 오래된 인증 프로토콜에서 OIDC/JWT 같은 신규 프로토콜로 넘어가는 과도기에 두 시스템을 계속 운영하면서 한쪽 토큰을 다른 쪽 토큰으로 교환하는 용도로 쓰인다. 우리의 "세션 쿠키 → JWT" 전환도 같은 문제(오래된 자격증명을 신규 자격증명으로 안전하게 바꿔주기)의 다른 형태이므로 같은 원리(전용 토큰 엔드포인트, 표준화된 요청/응답 파라미터)를 그대로 적용할 수 있다.
- **쿠키 설계 — 도메인/경로 공유**: 위 "CDN 리버스 프록시" 절의 그림처럼 레거시 JSP와 신규 Next.js가 같은 도메인 아래 다른 경로에 공존하므로, 레거시 세션 쿠키와 신규 JWT 저장용 쿠키(`HttpOnly`, `Secure`, `SameSite=Lax` 권장)의 `Domain`/`Path` 속성을 계획적으로 맞춰야 사용자가 두 경로를 오가도 다시 로그인하지 않는다. 이 설계를 빼먹으면 "경로만 분기했을 뿐인데 로그인이 자꾸 풀린다"는 형태로 CDN 리버스 프록시 전략 자체가 체감상 실패한 것처럼 보일 수 있다.
- **Gateway에서 인증 표준화**: API Gateway/BFF가 JWT 검증을 한 곳에서 처리하고, 그 뒤의 각 서비스(잡서비스 API, DMZ API)는 Gateway가 이미 검증한 사용자 식별자·권한 클레임을 헤더로 전달받아 신뢰하기만 한다 — 서비스마다 인증 로직을 중복 구현하지 않는다.
- **구현 선택지**: 과도기(1~1.5단계)에는 자체 토큰 엔드포인트(Spring Security/Spring Authorization Server 등)로 브릿지를 직접 구성하는 편이 빠르다. 레거시 JSP 로그인 로직 자체를 걷어내고 AWS Cognito 등 외부 IdP로 완전히 이관하는 것은, 로그인 화면이 Next.js로 넘어가는 2단계(도메인/인프라 이관) 이후가 현실적이다.
- **적용 순서**: 마이그레이션 단계 1(API 우선 구축)에서 vanilla JS가 신규 API를 처음 호출하는 시점부터 이 브릿지가 필요하다 — 지금 신규 API에 인증이 없으면 그 자체로 무방비 상태이므로, "인증/세션 정리"(단계 2)를 프론트 전환(2단계)까지 미루지 않고 API 우선 구축과 병행해 앞당긴다.

## 마이그레이션 단계

0. **클라우드 이용 규제 대응 착수 (선행 게이트, 실제 AWS 워크로드 투입 전)** — 아래 "클라우드 이용 전 규제 절차" 절의 중요도 평가부터 먼저 수행해, 스크래핑/잡서비스 컨테이너 이관·DMZ API 구축처럼 고객 데이터가 AWS로 넘어가는 첫 워크로드가 투입되기 전에 필요한 안전성 확보조치·계약서 요건을 인프라 설계(IaC)에 미리 반영한다. 특정 단계 하나에 속하지 않고 2·6~9단계 전체에 선행하는 게이트라서 번호를 매기지 않는다.
1. **API 우선 구축 (현재 단계)** — 모놀리식은 유지한 채 신규 API를 추가하고, 기존 JSP 프론트는 vanilla JS로 이 API들과 연동. 이 단계의 API 서비스부터 CI/CD를 우선 구축한다. **기존 JSP 로직을 API로 옮기기 직전에는** 위 "레거시 코드 안전망" 절의 캐릭터라이제이션 테스트로 현재 동작을 먼저 스냅샷으로 고정한다.
2. **인증/세션 정리** — 세션 기반 인증과 신규 API 인증 방식을 정리해, 이후 단계에서 프론트를 옮겨도 인증이 끊기지 않도록 설계한다. 구체적인 브릿지 방식은 위 "인증 전환 상세" 절 참고 — 1단계(API 우선 구축)와 병행해 앞당긴다.
3. **DMZ API 설계·구축** — 폐쇄망 DB 접근을 API로 추상화. 금융보안원 Multi-VPC(DMZ/내부망 + Transit Gateway) 패턴을 참고해 구성.
4. **클라우드-폐쇄망 연결 방식 확정 (옵션 A/B)** — 법무/컴플라이언스팀 검토 결과에 따라 AWS PrivateLink/Direct Connect(옵션 A) 또는 mTLS·IP 화이트리스트·WAF 기반 퍼블릭 엔드포인트/VPN(옵션 B)으로 클라우드와 폐쇄망을 연결.
5. **관측성/IaC 기반 마련** — 이후 단계의 잦은 배포·인프라 변경을 안전하게 반복하기 위한 선행 작업. 관측성의 구체적인 도구·경계 문제는 아래 "관측성 구체화" 절 참고.
6. **도메인/인프라 클라우드 이관** — 도메인을 AWS로 옮겨 경로 기반 라우팅 등 클라우드 네이티브 구성이 가능해지도록 준비.
7. **Next.js 전환 및 ECS 배포** — 클라우드로 옮긴 도메인 위에서 프론트엔드를 Next.js로 전환하고 ECS(Fargate)에 배포. CI/CD를 프론트에도 확장(이미지 빌드 → ECR → ECS 롤링 업데이트).
8. **스크래핑/잡서비스 컨테이너화 및 이관** — 배치성 워크로드를 이벤트 기반 스케줄링으로 전환.
9. **(장기) 마이크로프론트엔드/슈퍼앱 확장** — 여러 마이크로서비스 화면을 하나의 프론트 셸로 통합.

## Java 1.8 → 17 업그레이드의 숨은 장벽: javax → jakarta 네임스페이스

Java 런타임을 1.8 → 11 → 17(LTS)로 올리는 것과 별개로, JSP/서블릿 기반 코드를 최신 프레임워크(Tomcat 10+, Spring Boot 3+) 위에서 API로 감쌀 때는 반드시 짚어야 할 장벽이 하나 더 있다. Jakarta EE 9(2020)부터 `javax.*` 패키지가 전부 `jakarta.*`로 이름이 바뀌었다(`javax.servlet` → `jakarta.servlet` 등 — Oracle의 "javax" 상표권 문제로 Eclipse 재단이 결정한 변경). 즉 Java 런타임만 올린다고 끝나는 게 아니라, 기존 JSP/서블릿 코드의 import 전체와, 의존 중인 서드파티 라이브러리(Hibernate 등)의 Jakarta EE 9+ 호환 버전 여부까지 함께 확인해야 한다.

- **영향 범위**: Java 11까지는 `javax.servlet`을 그대로 쓸 수 있어 당장 문제가 되지는 않지만, 신규 프레임워크 버전(Tomcat 10+, Spring Boot 3+)으로 옮기는 시점에는 반드시 마주친다 — "JSP를 API로 감싼다"는 스트랭글러 작업이 결국 이 지점을 통과하므로 로드맵에 미리 반영해둔다.
- **완화 방법**: 수작업 치환 대신 OpenRewrite의 Jakarta 마이그레이션 레시피 모음([`rewrite-migrate-java`](https://github.com/openrewrite/rewrite-migrate-java))으로 네임스페이스 변경을 자동화할 수 있다 — Spring Boot 팀도 [3.0 마이그레이션 가이드](https://spring.io/blog/2022/05/24/preparing-for-spring-boot-3-0)에서 OpenRewrite 기반 도구를 공식 권장한다.
- **점검 항목**: 서드파티/사내 라이브러리가 Jakarta EE 9+ 호환 버전을 제공하는지 사전 조사 (오래된 라이브러리는 호환 버전이 없을 수 있다).

## 레거시 코드 안전망: Characterization Test

JSP 로직을 API로 감싸기(스트랭글러 패턴) 전에 반드시 짚어야 할 선행 작업이 있다. 지금의 JSP/서블릿 코드는 대부분 테스트가 없는 상태로 운영되어 왔을 가능성이 높다 — "무엇을 리팩터링해도 되는지"를 판단할 기준 자체가 없다는 뜻이다. Michael Feathers가 [『Working Effectively with Legacy Code』](https://en.wikipedia.org/wiki/Working_Effectively_with_Legacy_Code)에서 제시한 **캐릭터라이제이션 테스트(characterization test, 골든 마스터 테스트)**가 이 문제에 대한 표준적인 해법이다.

- **개념**: "이 코드가 무엇을 해야 하는가"가 아니라 "지금 실제로 무엇을 하는가"를 그대로 테스트로 고정한다. 기존 JSP/서블릿 로직에 실제 운영 입력값(또는 대표 샘플)을 넣어 나온 출력을 "정답(golden master)"으로 저장해두고, 이후 API로 옮긴 코드가 같은 입력에 같은 출력을 내는지 자동으로 비교한다. 로직이 옳은지 그른지 판단하지 않고, **행동이 의도치 않게 바뀌지 않았는지**만 보장한다.
- **왜 필요한가**: 스트랭글러 패턴으로 JSP를 API로 옮기는 작업은 본질적으로 "동작을 그대로 유지하면서 껍데기만 바꾸는" 리팩터링이다. 테스트 없이 이 작업을 하면 옮기는 과정에서 생긴 미묘한 로직 차이(반올림 방식, null 처리, 날짜 경계값 등)를 발견할 방법이 없다.
- **Shadow Traffic 검증과의 관계**: 캐릭터라이제이션 테스트는 **배포 전** 개발자 로컬/CI 단계에서 알려진 입력값으로 빠르게 회귀를 잡는 안전망이고, Shadow Traffic(위 리스크 항목의 GitHub Scientist 방식)은 **운영 트래픽**으로 미처 예상 못한 실제 입력값까지 검증하는 안전망이다. 두 단계가 상호 보완적이다 — 캐릭터라이제이션 테스트로 알려진 회귀를 먼저 걸러낸 코드만 Shadow Traffic 검증 단계로 올린다.
- **적용 방법**: 신규 API로 옮길 JSP 핸들러 단위로, 대표적인 실제 요청/응답 쌍(개인정보는 마스킹·익명화)을 골든 마스터로 수집 → API 전환 후 동일 입력에 대해 자동 비교하는 회귀 스위트를 구성한다. [ApprovalTests](https://approvaltests.com/) 계열 도구가 이 패턴(입출력을 스냅샷으로 저장하고 diff로 승인/거부)을 언어 무관하게 지원한다.
- **적용 순서**: 마이그레이션 단계 1(API 우선 구축)에서 신규 API를 만들기 **직전**에, 옮길 JSP 로직에 대한 캐릭터라이제이션 테스트부터 작성한다 — 테스트가 없는 상태로 먼저 리팩터링부터 시작하지 않는다.

## CI/CD 파이프라인 설계

목표 3(CI/CD 구축)은 지금까지 "API 서비스부터 우선 구축한다"는 순서만 정해져 있었다. 실제 파이프라인 단계를 위에서 이미 다룬 안전망(캐릭터라이제이션 테스트, 카나리, Shadow Traffic)과 엮어 하나의 흐름으로 정리하면 다음과 같다.

1. **PR 단계** — lint/typecheck/단위 테스트를 실행한다. JSP 로직을 API로 옮기는 PR은 위 "레거시 코드 안전망" 절의 캐릭터라이제이션 테스트를 회귀 게이트로 함께 돌려, 골든 마스터 대비 출력이 달라졌는지 확인한다. 이 단계에 SCA(Software Composition Analysis)·SAST(정적 분석) 스캔도 함께 넣는다 — 자세한 근거는 아래 "보안 스캐닝" 절 참고.
2. **빌드** — main/develop 머지 시 커밋 SHA를 태그로 컨테이너 이미지를 빌드해 ECR에 푸시한다(위 "왜 컨테이너(ECS)인가"의 "배포 = 이미지 교체" 참고).
3. **스테이징 배포** — IaC(Terraform)로 구성한 스테이징 환경에 ECS 롤링 업데이트로 배포하고 통합/E2E 테스트를 돌린다.
4. **프로덕션 배포** — 위험도가 있는 변경(신규 API로 옮긴 JSP 로직, 런타임 업그레이드 등)은 두 안전망을 함께 쓴다.
   - **카나리**: 신규 이미지를 일부 ECS 태스크에만 먼저 배포하고, 지표(에러율/지연시간)에 이상이 없을 때만 나머지 태스크로 확대한다.
   - **Shadow Traffic**: 위 "레거시 코드 안전망" 절에서 다룬 Scientist 패턴처럼, 신규 코드(candidate)를 프로덕션 트래픽에 함께 실행하되 응답은 기존 로직(control)만 반환하고 차이를 비동기로 비교한 뒤 완전 전환한다.
5. **롤백** — 문제가 생기면 이전 이미지 태그로 ECS 서비스만 업데이트하면 즉시 되돌아간다. 이미지가 불변(immutable)이라 별도 롤백 스크립트나 데이터 복구 절차 없이 배포 자체를 되돌리는 것으로 충분하다.
6. **배포 후 관측** — CloudWatch 대시보드/알람에 배포 이벤트를 연결해, 배포 직후 에러율·지연시간 급증을 자동으로 감지한다.

API 서비스를 먼저 이 6단계로 태우는 이유는 배포 단위가 작아 파이프라인 자체를 검증하는 리스크가 낮기 때문이다. 여기서 검증된 파이프라인을 그대로 Next.js 프론트(2단계)와 스크래핑/잡서비스 컨테이너화에도 재사용한다 — 컨테이너 배포 방식을 통일한 선택(위 "왜 컨테이너(ECS)인가")이 CI/CD 파이프라인을 서비스마다 새로 설계하지 않아도 되게 만드는 지점이다.

## 보안 스캐닝: SCA/SAST를 PR 게이트에

위 CI/CD 파이프라인의 PR 단계는 지금까지 lint/typecheck/단위 테스트와 캐릭터라이제이션 테스트만 다뤘다. Java 1.8 기반 레거시 코드를 API로 감싸는 작업은 오래된 서드파티 라이브러리(오래 방치된 Hibernate, Spring 구버전 등)를 그대로 재사용하는 경우가 많아, 알려진 취약점(CVE)이 파이프라인 어디에서도 걸러지지 않은 채 그대로 API로 노출될 위험이 있다.

- **SCA(Software Composition Analysis)** — 의존성 목록(Maven `pom.xml`/Gradle 등)을 스캔해 NVD(National Vulnerability Database) 기준 알려진 취약점이 있는 라이브러리를 찾아낸다. [OWASP Dependency-Check](https://owasp.org/www-project-dependency-check/)는 Maven/Gradle/Jenkins 플러그인을 모두 지원해 별도 SaaS 계약 없이 PR 게이트에 바로 넣을 수 있다 — 신규 API뿐 아니라 **기존 JSP/서블릿 모듈의 의존성부터 먼저 스캔**해, "API로 감싸기 전에 이미 알려진 취약점이 있었는지"를 로드맵 착수 시점에 파악해둔다.
- **SAST(Static Application Security Testing)** — 신규 API 코드에 대해 SQL 인젝션, 시크릿 하드코딩(아래 "시크릿 관리" 절 참고) 같은 패턴을 정적으로 탐지한다. SonarQube 등 기존에 코드 품질 게이트로 쓰는 도구가 보안 룰셋도 함께 제공하는 경우가 많아, 별도 도구를 새로 들이지 않고 기존 정적 분석 파이프라인에 룰만 추가하는 방향을 우선 검토한다.
- **컨테이너 이미지 스캐닝** — 위 "왜 컨테이너(ECS)인가" 절에서 다뤘듯 모든 서비스를 컨테이너 이미지로 배포하기로 한 이상, SCA·SAST가 보지 못하는 취약점이 하나 더 남는다. SCA는 애플리케이션이 직접 선언한 의존성(Maven/npm 등)만, SAST는 우리가 작성한 코드만 보므로, **베이스 이미지(OS 패키지, 언어 런타임 자체)**에 있는 취약점은 둘 다 놓친다. Amazon ECR의 이미지 스캐닝(Basic scanning은 기본 제공, Enhanced scanning은 Amazon Inspector 기반으로 이미 푸시된 이미지도 새 CVE가 공개될 때마다 자동 재스캔)으로 이 구멍을 메운다. PR 단계에서는 아직 이미지가 존재하지 않으므로, 이 스캐닝은 SCA/SAST와 달리 PR 게이트가 아니라 위 CI/CD 6단계 중 **빌드 단계**(ECR 푸시 직후)에 넣고, [Trivy](https://github.com/aquasecurity/trivy) 같은 오픈소스 스캐너로 CRITICAL/HIGH 등급 취약점이 나오면 그 자리에서 파이프라인을 실패시켜 배포 자체를 막는다.
- **적용 순서**: 마이그레이션 단계 1(API 우선 구축)에서 CI/CD 6단계를 처음 구축하는 시점에 SCA부터 PR 게이트에 넣는다 — 신규 코드가 없어도 기존 레거시 의존성 목록만으로 바로 실행 가능해 가장 빠르게 가치를 낼 수 있다. SAST는 신규 API 코드가 쌓이기 시작하는 시점에 이어서 추가한다. 컨테이너 이미지 스캐닝은 같은 1단계에서 신규 API를 처음 컨테이너화해 ECR에 이미지를 푸시하기 시작하는 시점부터 scan-on-push로 함께 켜, "이미지가 존재하는 순간부터 스캔되지 않는 공백"이 생기지 않게 한다.
- **오탐(false positive) 관리**: OWASP Dependency-Check는 오탐률이 상대적으로 높은 편이라, 검토 후 오탐으로 확인된 항목은 suppression 파일로 관리해 매 PR마다 같은 오탐을 다시 검토하지 않게 한다.

## 시크릿 관리: 하드코딩에서 런타임 주입으로

지금까지 인증/DMZ API/CI·CD 각 절에서 DB 접속정보, JWT 서명 키, 외부 연동 키 같은 자격증명이 계속 등장했지만, "이 값들을 실제로 어디에 어떻게 저장하는가"는 다루지 않았다. 레거시 JSP 모놀리스는 보통 이런 값을 `.properties` 설정 파일이나 소스에 평문으로 두고 서버에 직접 배포하는 방식을 쓴다 — 온프레미스 서버 접근 자체가 제한적이라는 전제 위에서 성립하던 방식이다.

- **컨테이너 전환이 만드는 새 위험**: 위 "왜 컨테이너(ECS)인가" 절에서 다뤘듯 배포 단위가 이미지로 바뀌면, 지금까지 하던 방식 그대로 자격증명을 코드/설정에 넣어 이미지를 빌드하는 실수가 생기기 쉽다. 컨테이너 이미지는 ECR 레지스트리에 계속 남고 여러 사람/파이프라인이 pull할 수 있어, 서버 접근을 제한하던 레거시 방식과 달리 이미지 접근 권한을 가진 누구나 평문 자격증명을 볼 수 있게 된다.
- **해법 — 런타임 주입**: 자격증명은 이미지에 구워넣지 않고 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/)(로테이션이 필요한 DB 자격증명 등)와 Systems Manager Parameter Store(로테이션이 필요 없는 설정값)에 나눠 저장한다. ECS 태스크 정의의 `secrets` 필드로 컨테이너 시작 시점에 환경변수로 주입받되, 이미지 자체와 소스 저장소에는 값이 전혀 남지 않는다.
- **최소 권한**: 태스크별 IAM 역할을 분리해, 각 태스크가 자신에게 필요한 시크릿에만 읽기 권한을 갖게 한다 — DMZ API 태스크가 프론트 태스크의 시크릿까지 읽을 수 있는 구조를 피한다.
- **자동 로테이션 우선순위**: DMZ API가 쓰는 폐쇄망 DB 자격증명처럼 민감도가 높은 값부터 Secrets Manager의 RDS/DB 자동 로테이션 기능을 적용한다. JWT 서명 키(위 "인증 전환 상세" 절의 토큰 교환 브릿지가 쓰는 키)도 같은 방식으로 주기적 로테이션 대상에 포함한다.
- **적용 순서**: 마이그레이션 단계 1(API 우선 구축)에서 신규 API를 만들 때부터 Secrets Manager/Parameter Store를 기본값으로 쓴다. 기존 JSP 설정 파일에 남아있는 하드코딩된 자격증명은 그 JSP 로직을 API로 옮기는 시점에 함께 Secrets Manager로 이관해, "일단 옮기고 나중에 정리"하는 부채를 만들지 않는다.

## 관측성 구체화: 폐쇄망 경계를 넘는 분산 추적

지금까지 관측성은 "구조화 로깅 + CloudWatch/APM"으로만 목표에 적혀 있었다. 우리 아키텍처는 요청 하나가 CloudFront → ALB → ECS(Next.js) → API Gateway/BFF → DMZ VPC → (Transit Gateway 또는 PrivateLink/mTLS) → 폐쇄망 내부의 DMZ API/레거시 API까지 여러 경계를 넘나든다. 이 경계마다 관측성이 끊기면 장애 원인 추적이 "이 요청이 어디서 느려졌는지" 수준에서 막힌다.

- **분산 추적 도구 선택**: AWS X-Ray는 트레이스 백엔드(저장·시각화)이고, OpenTelemetry(OTel)는 계측·수집 프레임워크로 역할이 다르다. [AWS Distro for OpenTelemetry(ADOT)](https://aws.amazon.com/about-aws/whats-new/2021/09/aws-availability-distro-opentelemetry-tracing-support)의 X-Ray Exporter를 쓰면 OTel로 계측한 트레이스를 X-Ray로 보낼 수 있어, 프론트(Next.js)·신규 API·DMZ API·(추후) 컨테이너화된 레거시 API까지 하나의 계측 표준(OTel)으로 통일하면서 저장은 X-Ray를 그대로 쓸 수 있다.
- **경계에서 끊기는 문제 — 트레이스 헤더 포맷**: X-Ray는 자체 헤더(`X-Amzn-Trace-Id`)를, OpenTelemetry는 W3C Trace Context(`traceparent`/`tracestate`)를 쓴다([참고: 분산 추적 — AWS 마이크로서비스 백서](https://docs.aws.amazon.com/whitepapers/latest/microservices-on-aws/distributed-tracing.html)). 두 포맷이 다르므로, 특히 DMZ API 앞단처럼 우리가 아직 통제하지 못하는 구간(레거시 JSP/서블릿 코드가 API로 안 감싸진 부분)을 지날 때 헤더 전파가 끊기면 추적이 거기서 끊긴다. ADOT Collector의 X-Ray 프로퍼게이터로 이 변환을 처리하되, 레거시 코드 쪽에는 헤더를 그대로 통과시키는 최소한의 프록시 설정이 필요하다.
- **네트워크 설정**: DMZ VPC/내부망 VPC 보안 그룹에 OTLP 트래픽용 포트(gRPC 4317, HTTP 4318)를 열어야 하고, X-Ray/CloudWatch용 VPC 엔드포인트를 구성해 텔레메트리 데이터가 인터넷 구간을 거치지 않고 AWS 서비스로 전달되게 한다 — 위 "AWS Private Network" 절의 옵션 A/B 논의와 같은 맥락의 결정이다.
- **프론트엔드 관측성(RUM)**: 서버 측 APM만으로는 "실제 사용자 브라우저에서 얼마나 느린지"를 못 본다. CloudWatch RUM(Real User Monitoring) 같은 도구로 Next.js 페이지의 실사용자 로딩 시간·JS 에러를 수집하는 것도 목표 1(SEO/GEO 렌더링 전략)의 실측 지표(Core Web Vitals 등)와 맞물린다.
- **적용 순서**: 마이그레이션 단계 5(관측성/IaC 기반 마련)에서, 신규 API부터 OTel 계측을 표준으로 넣고 X-Ray로 수집 → DMZ API 구축 시점에 경계를 넘는 트레이스 전파를 검증 → Next.js 전환 시 RUM을 추가하는 순서로 확장한다.

## 클라우드 이용 전 규제 절차: 전자금융감독규정 제14조의2

지금까지 클라우드 전환의 법적 제약은 "AWS Private Network(PrivateLink/Direct Connect)가 국내 법규상 가능한가"라는 질문으로만 다뤄졌다(위 "AWS Private Network" 절 참고). 하지만 그 질문과 별개로, 금융회사가 개인신용정보·고유식별정보를 처리하는 업무를 클라우드컴퓨팅서비스로 옮기려면 그 자체로 전자금융감독규정 제14조의2가 정하는 절차를 거쳐야 한다 — PrivateLink 허용 여부와 무관하게, AWS 리전에서 고객 데이터를 다루는 워크로드(스크래핑/잡서비스 이관, DMZ API 구축, 프론트엔드가 세션·개인정보를 다루는 경로 등)를 옮길 때마다 공통으로 적용되는 절차다.

**2025년 2월 5일 시행된 개정판** 기준 절차는 다음과 같다.

1. **중요도 평가** — 클라우드로 옮기려는 업무의 규모·복잡성, 클라우드 중단 시 영향, 전자적 침해행위 발생 시 고객에게 미치는 영향, CSP(클라우드서비스제공자) 종속 위험, 금융회사의 내부통제 역량 등을 종합해 해당 업무를 "중요업무"/"비중요업무"로 분류한다. 우리 워크로드 중 DMZ API(폐쇄망 DB 접근)와 스크래핑/잡서비스는 고객 재무 데이터를 직접 다루므로 중요업무로 분류될 가능성이 높고, 정적 콘텐츠 위주의 프론트엔드 화면은 비중요업무 쪽에 가까울 수 있다 — 실제 분류는 보안팀·법무팀과 사전 협의가 필요하다(확인 필요).
2. **차등 절차** — 중요업무는 CSP 건전성·안전성 평가, 업무연속성계획(BCP), 안전성 확보조치, 클라우드 위수탁 계약서의 법정 기재사항까지 모두 갖춰야 한다. 비중요업무는 이 절차가 대폭 간소화된다 — 2024~2025년 개정으로 유사·중복 평가항목도 141개에서 54개로 정비됐고, SaaS 형태 클라우드에는 별도 완화 기준이 마련됐다.
3. **보고** — 과거에는 중요업무 이용 시 실제 이용 개시 **7영업일 전 사전보고**가 의무였다. 개정 후에는 **사후보고**로 전환되어, 사유 발생일로부터 3개월 이내(계약 관련 변경사항은 7영업일 이내)에 금융감독원장에게 보고하면 된다 — 클라우드 전환 착수의 적시성이 그만큼 개선됐다는 뜻이다.

**로드맵에 반영할 점**: 이 절차는 법무팀의 PrivateLink/Direct Connect 적법성 검토(위 "AWS Private Network" 옵션 A/B 논의)와는 별개의, 반드시 거쳐야 하는 절차다. 위 "마이그레이션 단계"의 실제 고객 데이터가 AWS로 이동하는 첫 시점(스크래핑/잡서비스 컨테이너 이관, DMZ API 구축 등, 단계 6~9) 전에 중요도 평가부터 먼저 수행해 필요한 안전성 확보조치·계약서 요건을 인프라 설계(IaC)에 미리 반영해야 재작업을 피할 수 있다.

## 리스크 및 고려사항

- 모놀리식과 신규 API가 공존하는 기간의 병행 운영 부담 (배포·장애 대응 이중화).
- 기존 JSP(세션 기반 인증)와 vanilla JS로 호출하는 신규 API 간 인증/세션 처리 방식을 먼저 정리해야, 이후 Next.js 전환 시 인증을 다시 설계하지 않아도 된다. **대응**: 위 "인증 전환 상세" 절의 토큰 교환(RFC 8693 기반) 브릿지로 세션↔JWT를 연결하고, CDN 리버스 프록시 구간에서는 쿠키 `Domain`/`Path`를 계획적으로 맞춰 경로를 오가도 재로그인이 발생하지 않게 한다.
- 점진적 페이지 단위 전환이 어려움 — 도메인이 클라우드 환경에 있지 않아 경로 기반 라우팅 구성이 현재는 불가능. **대응**: 위 "CDN 리버스 프록시" 방식으로 도메인 완전 이관 전에도 경로 기반 라우팅을 선제적으로 확보할 수 있다.
- 기존 JSP 로직을 API로 감쌀 때 신구 결과가 어긋나면 사용자에게 바로 노출된다. **대응**: GitHub이 자사 권한/결제 로직을 리팩터링할 때 쓴 [Scientist](https://github.com/github/scientist) 같은 shadow-traffic 검증 방식 — 신규 코드(candidate)를 실제 프로덕션 트래픽에 함께 실행하되 응답은 기존 로직(control) 결과만 사용자에게 반환하고, 둘의 차이를 비동기로 수집·비교해 안전하게 검증한 뒤 전환한다.
- Next.js를 ECS에서 상시 실행하는 구조는 정적 호스팅보다 운영 부담(스케일링 정책, 헬스체크, 이미지 관리)과 비용이 크다. **대응**: 위 "왜 컨테이너(ECS)인가"의 판단 근거를 전환 착수 전에 팀과 합의하고, 렌더링이 필요 없는 화면은 SSG로 빌드해 CloudFront에서 바로 서빙해 ECS 부하를 줄인다.
- SSR·CSR을 화면/컴포넌트 단위로 명확히 구분해서 개발해야 해, 순수 CSR SPA보다 개발 복잡도가 올라간다. **대응**: 위 "왜 Next.js인가"의 SSR/CSR 구분 기준을 컨벤션으로 문서화하고, 코드 리뷰에서 의도치 않게 클라이언트 컴포넌트로만 짜여 실질적 CSR이 되어버리는 화면을 걸러낸다.
- 금융 데이터 특성상 DMZ API와 Private Network 구간의 보안 검토(제로트러스트, 접근 통제)가 일정에 선행되어야 한다.
- PrivateLink/Direct Connect 등 AWS Private Network 연결이 국내 법규상 어려울 가능성이 있음(확인 필요 — 법무팀 검토 필요). 이 경우를 대비해 대안(옵션 B: mTLS/IP 화이트리스트/WAF 기반 퍼블릭 엔드포인트, VPN 등)으로 전환할 준비를 함께 갖춰야 한다.
- 위 PrivateLink 적법성 검토와는 별개로, 고객 데이터를 다루는 워크로드(스크래핑/잡서비스, DMZ API 등)를 클라우드로 옮길 때마다 전자금융감독규정 제14조의2에 따른 중요도 평가·안전성 확보조치·보고 절차를 거쳐야 한다(확인 필요 — 실제 업무별 중요도 분류는 보안팀·법무팀 협의 필요). 자세한 내용은 위 "클라우드 이용 전 규제 절차" 절 참고.
- Feature flag를 도입하면 완전 전환 후에도 플래그와 신구 분기 코드가 정리되지 않고 남는 **플래그 부채(flag debt)** 리스크가 생긴다. **대응**: 각 flag를 만들 때 "100% 전환 후 이 flag와 레거시 분기를 제거한다"를 마이그레이션 완료 조건에 포함하고, 오래된 flag를 주기적으로 점검한다.
- 컨테이너 전환 과정에서 자격증명을 이미지/소스에 그대로 구워넣으면, 레지스트리 접근 권한을 가진 누구나 평문 자격증명을 볼 수 있는 새로운 유출 경로가 생긴다. 레거시 JSP도 알려진 취약점이 있는 오래된 서드파티 라이브러리를 그대로 쓰고 있을 가능성이 있다. **대응**: 위 "시크릿 관리" 절의 Secrets Manager/Parameter Store 런타임 주입을 CI/CD 착수 시점부터 기본값으로 적용하고, 위 "보안 스캐닝" 절의 SCA(OWASP Dependency-Check)로 레거시 의존성의 알려진 CVE를 PR 게이트에서 먼저 걸러낸다.
- 팀의 기존 역량이 JSP/Java 1.8과 온프레미스 서버 직접 배포에 맞춰져 있어, 이번 로드맵이 요구하는 새 스택(React/Next.js, Terraform 등 IaC, 컨테이너 오케스트레이션, 분산 추적)은 도구를 바꾸는 정도가 아니라 팀 역량 자체의 전환을 요구한다 — 특히 Next.js/React는 기존 JSP 개발자에게는 겹치는 부분이 거의 없는 새 학습 영역이다. **대응**: 마이그레이션 단계 1(API 우선 구축)의 신규 API부터 Java 11/17·컨테이너·IaC를 작은 규모로 먼저 실전 경험하게 해, 2단계(Next.js/ECS 전면 전환)에서 학습 곡선과 마이그레이션 자체가 동시에 몰리지 않게 앞당겨 소화한다. 프론트엔드 역량은 내부 전환 교육으로 채울지 신규 채용으로 보완할지를 2단계 착수 전에 결정해야 한다(확인 필요).
