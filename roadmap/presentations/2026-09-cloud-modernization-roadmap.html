Why Now

왜 지금인가

REGULATION

망분리 규제 완화 흐름

2022년 금융위원회 「금융분야 클라우드 및 망분리 규제 개선방안」 발표 이후 2023년 전자금융감독규정이 개정되며, 금융회사의 상용 클라우드 이용 절차가 이전보다 명확해짐. 금융보안원은 9개 CSP와 협업해 클라우드 보안 관리 참고서를 배포.

INDUSTRY

업계는 이미 이동 중

국내 주요 은행 상당수가 컨테이너화를 넘어 CI/CD 기반 배포 자동화와 관측 가능성 확보를 포함한 클라우드 네이티브 방식을 채택하는 추세. 전환 과정의 최대 병목은 기술 인력 부재 — 우리도 역량 확보를 로드맵에 포함해야 함.

BUSINESS

배포 속도가 곧 경쟁력

신규 개발 후 빠르게 배포해야 하는 상황이 반복되고 있음. 이것이 CI/CD 구축의 직접적인 배경이며, 지금 시작하지 않으면 격차가 계속 벌어짐.

RISK

레거시 스택의 숨은 비용

Java 1.8/JSP는 최신 보안 패치, 라이브러리 생태계, 채용 시장 모든 면에서 유지비용이 계속 상승 중. 늦출수록 전환 난이도와 리스크가 커짐.

프론트엔드 현대화 — JSP·Java 1.8 → Next.js

목표

  • 기존 JSP를 API로 전환해 로직을 재활용 (다시 만들지 않는다)
  • 화면은 Next.js로 새로 구성 — JSP가 하던 서버사이드 렌더링을 SSR/SSG가 이어받아 SEO뿐 아니라 GEO(생성형 엔진 최적화)까지 고려한 렌더링과 슬러그 기반 URL 설계 확보
  • 인증 토큰·내부 API 주소를 브라우저에 노출하지 않고 서버 측에서 처리 → DMZ API 구조와 잘 맞음
  • 세션 기반 인증 → 토큰 기반 인증으로 점진 전환

전환 전략

  • 1단계(현재) — 모놀리식 유지, 신규 API 지속 추가. 기존 JSP는 vanilla JS로 신규 API와 연동
  • 1.5단계 — CloudFront를 온프레미스 앞단에 두는 리버스 프록시로, 도메인 완전 이관 전에도 경로 단위 전환 시작
  • 2단계 — 도메인/인프라를 클라우드로 이관한 뒤 Next.js 전환, ECS(Fargate)로 배포

Why Next.js

왜 Next.js인가

SSR이 CSR보다 SEO에 유리

CSR(순수 SPA)은 브라우저가 JS를 실행해야 콘텐츠가 채워져, 크롤러가 빈 HTML만 보고 색인에 실패할 수 있다. Next.js는 서버사이드 렌더링을 기본 지원해 JSP가 갖고 있던 SEO 이점을 그대로 이어받는다.

대가 — 개발 복잡도 상승

어떤 화면·컴포넌트를 서버에서 렌더링(SSR)하고 어떤 것을 브라우저에서 렌더링(CSR)할지 명확히 나눠서 설계·개발해야 한다. 아무 컴포넌트나 클라이언트 컴포넌트로 짜면 실질적으로 CSR SPA가 되어버려 도입 의미가 사라진다.

대응 — SSR/CSR 구분 기준을 컨벤션으로 문서화하고, 코드 리뷰에서 의도치 않은 CSR화를 걸러낸다.
항목CSR (순수 SPA)SSR (Next.js 기본)
SEO / 초기 렌더링빈 HTML → 크롤러 색인 실패 위험완성된 HTML을 바로 수집
서버 부하 / 비용정적 호스팅으로 충분ECS 상시 서버 필요 (SSG/ISR로 완화)
로딩 vs 전환 속도첫 로딩 느림 / 전환 매우 빠름첫 로딩 빠름 / 전환은 별도 최적화 필요
개발/디버깅 복잡도브라우저 하나 — 단순서버·클라이언트 이중 실행 — 하이드레이션 이슈
캐싱 전략번들 단위 CDN 캐싱화면별 SSR/SSG/ISR 세밀 제어

SEO/GEO 이점 때문에 SSR 기본 채택 + 변경 적은 화면은 SSG/ISR + 인터랙션 위주 화면만 의도적으로 CSR.

Why Containers

왜 컨테이너(ECS)인가

프론트(Next.js) · 신규 API · 스크래핑/잡서비스를 모두 같은 방식으로 배포한다 — 이미지 빌드 → ECR → ECS.

환경 동일성

런타임·라이브러리·설정이 이미지에 함께 담긴다. 지금처럼 "그 서버에서만 되는" 상태가 사라지고 로컬·스테이징·운영이 같은 것을 실행.

배포 = 이미지 교체

롤백은 이전 이미지 태그로 되돌리면 끝. 배포가 무겁고 되돌리기 어려운 지금 문제의 직접적인 해법.

CI/CD와 직결

빌드 → ECR 푸시 → ECS 업데이트가 그대로 파이프라인. 롤링/블루-그린 무중단 배포와 자동 롤백이 기본값.

오토스케일링

트래픽에 따라 태스크 수를 조절. 피크에 맞춘 서버를 상시 띄워둘 필요가 없다.

서버 관리 부담 감소

Fargate를 쓰면 EC2 인스턴스·OS 패치·AMI 관리가 사라진다. 인프라 인력이 얇을수록 효과가 크다.

리소스 격리

스크래핑 배치가 튀어도 프론트/API 자원을 잠식하지 않는다. 지금은 같은 서버 자원을 나눠 쓰는 구조.

런타임 업그레이드 실험

Java 11 → 17 같은 전환을 이미지 태그만 바꿔 일부 태스크에 먼저 태워보고(카나리) 즉시 되돌릴 수 있다.

이식성

같은 이미지를 클라우드와 폐쇄망 양쪽에서 실행. DMZ API처럼 위치가 바뀔 수 있는 구성 요소의 재작업이 줄어든다.

대가

이미지·레지스트리·오케스트레이션 학습 비용, ECS 상시 실행에 따른 운영 부담·비용 증가.

판단 — 어차피 스크래핑/잡서비스는 컨테이너화가 필요하다. 프론트만 다른 방식이면 CI/CD·관측성·롤백을 두 벌로 유지해야 한다.

개선 영역 3 / 4

CI/CD 환경 구축

목표

  • 배포 속도와 안정성을 동시에 확보
  • API 서비스부터 우선 구축 — 프론트 CI/CD는 클라우드 이관과 함께
  • GitHub Actions / AWS CodePipeline + IaC(Terraform)로 인프라도 코드로 관리

왜 API가 먼저인가

  • 모놀리식 프론트는 배포 단위가 커서 파이프라인 효과가 늦게 나타남
  • API는 상대적으로 독립적으로 배포 가능해 CI/CD 도입 효과를 빠르게 체감
  • 이후 DMZ API, 폐쇄망 연결 구성도 같은 파이프라인으로 관리

파이프라인 6단계

  • PR 게이트 — lint/typecheck/단위 테스트 + 캐릭터라이제이션 테스트(JSP→API 전환 구간의 회귀 확인)
  • 빌드 — 커밋 SHA 태그로 이미지 빌드 → ECR 푸시
  • 스테이징 배포 — IaC로 구성한 스테이징에 ECS 롤링 업데이트 + 통합/E2E 테스트
  • 프로덕션 배포 — 카나리(일부 태스크 우선 배포) + Shadow Traffic(신구 로직 비동기 비교) 병행. 배포(이미지)와 노출(사용자 비율)은 feature flag로 분리 제어
  • 롤백 — 이전 이미지 태그로 ECS 서비스만 업데이트하면 즉시 복구
  • 배포 후 관측 — CloudWatch 알람과 배포 이벤트를 연결해 에러율/지연시간 급증 자동 감지

폐쇄망 극복 — DMZ API & AWS Private Network

목표

  • 폐쇄망 DB 접근용 DMZ API 개발
  • AWS Private Network(PrivateLink/Direct Connect, 옵션 A)로 폐쇄망 환경 극복 — 국내 법규상 가능 여부 법무팀 검토 필요(확인 필요)
  • 검토 결과 어려울 경우 mTLS·IP 화이트리스트·WAF 기반 퍼블릭 엔드포인트(옵션 B)로 대체

근거 · 표준 패턴

  • 금융보안원 「금융분야 상용 클라우드서비스 보안 관리 참고서」의 Multi-VPC(DMZ VPC / 내부망 VPC + Transit Gateway) 패턴 채택
  • AWS PrivateLink는 Network Load Balancer를 통해 온프레미스 자원을 VPC 엔드포인트처럼 노출 — 인터넷 구간 미경유
  • 2022~2023년 전자금융감독규정 개정으로 관련 절차가 이전보다 명확해짐

Research Findings

추가로 발견한 개선 기회

인증 체계 통합

세션 기반(JSP) → 토큰 기반(JWT/OAuth2). API Gateway 단에서 통합해 프론트 입장에서는 단일 인증 흐름으로.

관측성 확보

구조화 로깅 + CloudWatch/APM. 폐쇄망 경계를 넘는 요청은 OpenTelemetry(ADOT)로 계측 통일 → X-Ray 수집, 경계에서 트레이스 헤더(X-Ray vs W3C Trace Context)가 끊기지 않게 프로퍼게이션 설정. 프론트는 CloudWatch RUM으로 실사용자 지표까지 확장.

Feature Flag 점진적 노출

CDN은 경로 단위(all-or-nothing)로만 신구를 나눈다 — 같은 경로 안에서 사용자 비율/세그먼트별로 신규 화면을 노출·즉시 롤백하려면 AWS AppConfig Feature Flags 같은 도구로 배포와 노출을 분리한다.

IaC 도입

Terraform 등으로 DMZ/Private Network 구성까지 코드화해 재현 가능하게 관리.

테스트 자동화

API 전환 직전 캐릭터라이제이션(골든 마스터) 테스트로 기존 JSP 로직의 실제 동작을 먼저 고정 → 이후 신구 API 병행 비교(shadow traffic).

API 문서화

JSP를 API로 전환할 때 OpenAPI 명세로 계약을 명확히 해 결합도를 낮춤.

배치 워크로드 컨테이너화

Java 버전 업그레이드

CDN 리버스 프록시로 조기 전환

Lesson Learned

서비스 분리, 어디까지가 적정선인가

사례내용우리에게 주는 시사점
Netflix 신규 가입자만 신규 서비스로 라우팅 → 세그먼트별 점진 이관 → 병행 비교 → 완전 전환. 700개 이상 마이크로서비스 운영. 스트랭글러 무화과 패턴이 서비스 중단 없이 대규모 전환을 가능하게 함 — 우리의 1→1.5→2단계 전략과 동일한 접근
Shopify 전면 마이크로서비스 대신 명시적 모듈 경계(Packwerk)를 둔 모듈러 모놀리스 채택 온보딩 시간 55% 단축, 모듈 간 회귀 68% 감소 — 잡서비스(API)처럼 도메인 경계가 아직 불명확한 영역은 무리하게 서비스부터 쪼개지 않는 선택지도 유효
Amazon Prime Video 과도하게 분산된 마이크로서비스를 단일 프로세스로 되돌림 인프라 비용 90% 절감 — 분리는 실제 배포 주기·트래픽 패턴 차이가 있는 경계에서만 의미가 있음
Capital One 8개 데이터센터를 모두 폐쇄하고 AWS로 전면 이관 — 재해복구 시간 70% 단축, 트랜잭션 오류 50% 감소, 개발 환경 구축 3개월→수 분 망분리·규제 제약에서 출발한 금융회사도 단계적으로는 완전한 클라우드 전환이 가능함을 보여주는 선례

Risks

리스크 및 대응

병행 운영 부담

모놀리식과 신규 API가 공존하는 기간 동안 배포·장애 대응이 이중화됨

대응 — 전환 단계별로 공존 기간을 최소화하고, 신규 API 우선 CI/CD로 배포 부담을 먼저 줄인다

인증/세션 불일치

JSP 세션 기반 인증과 신규 API 토큰 기반 인증이 과도기에 공존

대응 — Next.js 전환 이전에 인증 방식을 먼저 정리해 재설계 비용을 없앤다

과도한 서비스 분리

잡서비스(API)를 성급하게 잘게 나누면 오히려 복잡도·비용 증가

대응 — 실제 배포 주기·트래픽 차이가 검증된 경계에서만 분리 (모듈러 모놀리스 우선 검토)

보안·컴플라이언스

금융 데이터가 오가는 DMZ API·Private Network 구간은 보안 검토가 선행되어야 하며, PrivateLink/Direct Connect 자체가 국내 법규상 어려울 가능성이 있음(확인 필요)

대응 — 금융보안원 가이드 준수, 제로트러스트 원칙 적용, 법무팀 사전 검토를 일정에 명시적으로 포함. 어려울 경우 mTLS/IP 화이트리스트 기반 옵션 B로 전환

Feature Flag 부채

완전 전환 후에도 플래그와 신구 분기 코드가 정리되지 않고 코드에 계속 남을 수 있음

대응 — flag를 만들 때부터 "100% 전환 후 flag·레거시 분기 제거"를 완료 조건에 포함하고 주기적으로 점검
