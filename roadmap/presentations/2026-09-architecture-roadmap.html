01 / 12 — 배경
Why Now

지금 바꿔야 하는 이유

배포

느리고 불편한 배포

화면과 서버 로직이 하나의 모놀리식(JSP + Java 1.8)에 결합되어 있어, 신규 개발 후 빠르게 배포해야 하는 상황에서도 배포 속도가 느림. CI/CD 부재가 직접적인 배경.

런타임

Java 8 지원 종료 임박

OpenJDK 8은 2026년 11월 커뮤니티 무상 업데이트가 종료됨. 그 이후에는 공개 보안 패치 없이 운영해야 하는 공백이 생길 수 있음.

인프라

폐쇄망 제약

핵심 데이터베이스 등 자원이 폐쇄망 내부에 있어 클라우드 서비스에서 직접 접근할 수 없음. 클라우드 전환 전에 반드시 해결해야 하는 구조적 제약.

확장성

재사용 불가능한 로직

JSP 안에 묻혀 있는 서버 로직이 API로 노출되어 있지 않아, 다른 서비스나 신규 화면에서 재사용할 수 없음.

04 / 12 — 핵심 과제
Key Initiatives

6가지 핵심 개선 과제

01

JSP → API 전환

기존 JSP 로직을 버리지 않고 API로 추출해 프론트·타 서비스에서 재사용.

02

React 전환

화면 렌더링을 서버 로직에서 분리, 프론트엔드를 React 기반 SPA로 재구성.

03

프론트 클라우드 전환

프론트엔드를 AWS 클라우드 서비스로 이전, 배포·확장 자동화.

04

CI/CD 구축

신규 API 서비스부터 빌드-테스트-배포 파이프라인 구축.

05

DMZ API 개발

폐쇄망 DB 접근 전용 API를 두어 클라우드-내부망 간 단일 통로 확보.

06

AWS Private Network

가능한 경우 PrivateLink/Direct Connect로 인터넷 노출 없이 폐쇄망 극복.

05 / 12 — 전환 전략
Migration Strategy

Strangler Fig 패턴 + BFF

빅뱅 전환 대신, 파사드를 통해 트래픽을 점진적으로 신규 구조로 옮긴다.

1단계 — 현재

모놀리식 구조 유지, 신규 기능은 API로 추가. 기존 JSP 화면은 vanilla JS로 신규 API와 연동. 도메인이 아직 클라우드에 없어 경로 기반 라우팅 전환은 불가능하므로, 페이지 단위 점진 전환 대신 API 우선 확장 전략을 취함.

2단계 — 클라우드 이관 이후

도메인/인프라를 AWS로 이관한 뒤 React 전환. BFF(Backend for Frontend) 계층을 두어 화면 전용 API 조합과, 레거시(세션 기반)·신규(API) 인증 방식 차이를 흡수.

Principle

파사드(API Gateway)가 처음에는 요청을 레거시로 그대로 전달하다가, 신규 서비스가 준비된 기능부터 하나씩 라우팅을 옮겨간다 — 레거시를 한 번에 걷어내지 않고 "천천히 교체"한다.

06 / 12 — 사례 연구
Lessons from the Field

실제 사례에서 배우는 교훈

실패 사례 — UI부터 바꾼 결과

레거시 JSP 화면을 신규 React 관리자 화면으로 옮기면서 화면 로직만 유지한 프로젝트가, 페이지 1회 호출에 레거시 모놀리식 API를 47회 호출하는 구조를 그대로 이어받아 성능·안정성 문제로 4개월 만에 중단(약 $680K 손실). → 시사점: 화면 전환보다 API 계약(BFF/집계 API) 정리가 먼저.

통계 — 초기 속도의 중요성

Strangler 패턴을 적용한 41개 기업 프로젝트 중 68%가 첫 90일 안에 첫 컴포넌트 전환도 마치지 못하고 정체됨. → 시사점: 작은 단위로 쪼개 90일 내 가시적 성과를 만드는 것이 프로젝트 존속에 직결.

성공 사례 — 점진적 전환의 효과

파사드 기반으로 기능 단위 점진 전환을 수행한 사례에서 재작업 비용 대비 큰 폭의 절감 효과가 보고됨(사례별 최대 수백만 달러 규모). 공통점은 "측정 가능한 작은 단위"와 "롤백 가능한 배포".

출처: vFunction, Modernization Intel, WunderGraph (상세 링크는 마지막 장 참고 자료 참조)

07 / 12 — 백엔드
Backend Modernization

스크래핑 서비스 · 잡서비스(API) 현대화

Runtime

Java 버전 업그레이드

Java 8 → 17(LTS) → 21(LTS) 단계적 업그레이드. Spring Boot 사용 시 2.7 → 3.x 브릿지(javax → jakarta 네임스페이스 전환 포함). OpenRewrite 등으로 기계적 변경 비용 절감.

Scraping

Job 기반 실행으로 전환

컨테이너화 후 Kubernetes Job/CronJob 기반 실행. 상시 기동 대신 실행한 만큼만 자원을 사용해 비용 효율화. 헤드리스 브라우저 워커는 오토스케일링 풀로 분리.

Job API

스케줄/실행 역할 분리

배치 스케줄·실행이력·선후행 제어와 실제 실행 자원(K8s)의 역할을 분리. 기존 JSP가 참조하던 로직은 API로 노출해 재사용 가능하게 전환.

08 / 12 — 안전망
Safety Net Before Refactor

바꾸기 전에 먼저 갖출 것

테스트와 관측성 없이 구조를 바꾸는 것은 개선이 아니라 도박이다.

특성화 테스트 / 골든 마스터 테스트

현재 시스템의 실제 동작(quirk 포함)을 고정해 회귀를 즉시 감지. 변경할 영역을 정하고, 실데이터에 가까운 입력으로 현재 출력을 캡처해 골든 파일 테스트로 전환한 뒤 리팩터링을 시작한다.

관측성 선(先) 구축

분산 트레이싱, 구조화된 로깅, 서비스 간 호출 지연 지표를 리팩터링 착수 전에 갖춘다. 지금 시스템이 어떻게 동작하는지 파악하지 못한 채 분해를 시작하지 않는다.

09 / 12 — 폐쇄망
Closed Network

폐쇄망 환경 극복

DMZ API

폐쇄망 내부 DB 접근이 필요한 요청은 DMZ에 위치한 전용 API로만 처리. 클라우드에서 폐쇄망 DB로의 직접 연결을 만들지 않고, DMZ가 유일한 통로 역할을 한다.

AWS Private Network

가능한 구간은 AWS PrivateLink / Direct Connect / Transit Gateway로 구성해 인터넷 구간 노출 없이 VPC 간 통신을 확보한다.

규제 동향

2024년 8월 금융위원회 "금융분야 망분리 개선 로드맵" 발표로 연구·개발망에 한해 논리적 망분리가 허용되는 등 완화 흐름이 있음. 국내 금융권 클라우드 실제 활용률은 아직 낮은 수준(글로벌 80%+ 대비)으로, 망분리 규제 대응이 도입 속도의 핵심 변수.
