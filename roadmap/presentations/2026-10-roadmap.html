선정산이란?

정의

온라인 플랫폼 판매자가 결제~정산 사이에 묶여 있는 판매대금을 앞당겨 정산받는 금융 서비스

대출이 아니다

이미 번 매출(정산금)을 양도하고 현금화하는 매출채권 팩토링 구조. 부채로 잡히지 않고 상환은 정산일에 자동 처리

왜 필요한가

소비자 결제 후 실제 정산까지 일정 기간이 걸려, 그동안 사업·광고·운영 자금이 막힘. 미리 받은 정산금은 이 용도로 활용

선정산이란?

종합 플랫폼 대응 (IT 관점)

왜 현대화가 필요하고, IT 관점에서는 무엇을 할 수 있는가?

선정산 (첫 시작 서비스) → 종합 플랫폼

IT 기반을 먼저 탄탄히

선정산은 종합 플랫폼의 첫걸음입니다. 앞으로 더해질 서비스를 받쳐 줄 토대를 지금부터 차근차근 만들어 갑니다.

서비스가 늘어납니다

서비스가 늘면 하나의 코드베이스를 여러 팀이 함께 고치게 되어 변경 충돌과 배포 부담이 커집니다. 개발 속도와 인력 확장에도 한계가 생깁니다.

모놀리식 → 마이크로서비스

서비스 단위로 나누어 팀별로 독립적으로 개발·배포할 수 있는 구조로 단계적으로 전환해 갑니다.

화면과 API 분리

JSP에 묶여 있던 화면과 로직을 나눕니다. 화면은 프론트엔드(React · Next.js)가, 로직은 백엔드(API)가 맡습니다.

세션 stateless 전환

서버 세션 대신 토큰(ex. JWT)으로 인증합니다. 어느 서비스로 요청이 가도 같은 방식으로 사용자를 확인할 수 있어, 서비스를 자유롭게 늘리고 나눌 수 있습니다.

경로 기반 라우팅

화면(example.com)과 API(api.example.com)를 도메인으로 나누고, 각각 그 아래에서 경로로 서비스를 나눕니다.

아키텍처 현대화

선정산 서비스 점진적 전환

지금의 모놀리식 선정산 서비스를 세 단계로 나누어 전환합니다. 이 과정에서 컨테이너를 도입합니다.

STEP 1

백엔드 API화

API는 있지만 응답 규격이 확립되어 있지 않고, 일부는 HTML을 응답합니다. 공통 JSON 응답 규격을 정해 적용하고, HTML 응답을 JSON으로 바꿉니다.

STEP 2

stateful → stateless

서버 세션에 의존하는 인증을 토큰(ex. JWT) 기반으로 바꿉니다. 어느 서비스에서든 같은 방식으로 사용자를 확인할 수 있게 합니다.

STEP 3

JSP → React(Next.js)

정리된 API 위에 화면을 React(Next.js)로 옮깁니다. L7이 도입되면 경로 단위로 나누어 넘길 수도 있습니다.

컨테이너 도입 효과

서비스를 실행 환경째로 묶어 배포합니다. 클라우드(AWS) 전환 가능성에 대비할 수 있고, 생각보다 무겁지 않습니다.

환경 일관성

로컬·개발·운영이 같은 이미지로 실행됩니다. "내 PC에서는 되는데" 같은 환경 차이가 사라집니다.

서버는 정답 데이터와 규칙을 책임지고, 화면에 어떻게 보여줄지는 프론트엔드가 책임집니다.

  • 시간·숫자 표시는 새 기술이 아니라 브라우저 표준(ISO 8601, Intl)을 따르는 것입니다. 서버가 UTC로 내려주므로 서버 시간대가 바뀌어도 화면 시간은 그대로입니다.

자세한 원칙과 코드 리뷰 체크리스트는 문서를 참고합니다.

* 국제화(i18n) — 사용자의 언어·지역에 맞게 시간·숫자·통화를 표시하는 것입니다. 브라우저에 내장된 Intl API로 별도 라이브러리 없이 처리합니다.

DB: Soft Delete 도입

데이터를 지우지 않고 삭제 일시만 기록합니다. DBA를 거치던 삭제·복구를 애플리케이션에서 처리합니다.

항목Hard Delete (현재)Soft Delete
삭제DELETE로 행 삭제UPDATE로 DELETED_AT 기록
복구DBA에게 백업 복원 요청UPDATE 한 번으로 개발자가 직접 복구
삭제 이력별도 이력 테이블 없으면 남지 않음DELETED_AT · DELETED_BY로 바로 조회
정책 변경DB 작업에 의존코드 배포로 반영

핵심 원칙

  • 조회·조인·집계·배치 쿼리에는 항상 DELETED_AT IS NULL 조건을 넣습니다.
  • 유니크 컬럼(아이디, 이메일 등)은 삭제할 때 delete_{PK}_원래값으로 바꿔 재가입 충돌을 막습니다.
  • PK는 삭제·복구 어느 단계에서도 수정하지 않습니다.

신규 테이블에만 적용하고 기존 테이블은 변경하지 않습니다. 삭제된 행은 기본적으로 영구 보관하고, 로그성 데이터만 보관 기간이 지나면 배치로 정리합니다.

주의 — 개인정보 파기 의무가 있는 데이터에는 그대로 적용할 수 없으므로, 보관 기간과 파기 방식을 법무·보안 담당과 먼저 협의합니다.

Soft Delete 예시

회원 hong이 탈퇴한 뒤 같은 아이디로 다시 가입하는 경우입니다.

시점USER_NOUSER_IDDELETED_AT
삭제 전1024hongNULL (정상)
삭제 후1024delete_1024_hong2026-10-01 14:30
재가입1107hongNULL (정상)

삭제는 UPDATE 한 번

UPDATE TB_USER
   SET USER_ID    = 'delete_' || USER_NO || '_' || USER_ID,
       DELETED_AT = SYSTIMESTAMP,
       DELETED_BY = :operator
 WHERE USER_NO = :userNo
   AND DELETED_AT IS NULL;

-- 조회는 항상 정상 행만
SELECT * FROM TB_USER WHERE DELETED_AT IS NULL AND USER_ID = :userId;

삭제된 행의 아이디에 delete_{PK}_를 붙여 유니크 제약을 비워 주므로 같은 아이디로 다시 가입할 수 있습니다. PK를 함께 붙여 여러 번 삭제해도 충돌하지 않습니다.

## 작업 순서
기능 구현·수정 요청은 아래 순서로 진행한다. 앞 단계를 통과해야 다음 단계로 넘어간다.

1. 코딩 — 화면은 senior-frontend-developer, 백엔드는 senior-java-developer에게 맡기고,
   standards/security-checklist.md 기준으로 보안 검토를 함께 한다.
2. 코드 리뷰 — code-reviewer 서브에이전트에게 변경 diff 리뷰를 맡기고, 지적 사항을 반영한다.
3. 테스트 — test-runner 서브에이전트로 테스트를 작성·실행한다. 실패하면 1단계로 돌아간다.
4. 문서화 — doc-writer에게 API 문서(OpenAPI)와 services/<서비스명>/ 문서 갱신을 맡긴다.

각 단계의 상세 기준은 지침에 쓰지 않고 경로로만 연결합니다. 보안 검토는 기본 제공되는 /security-review 명령도 활용할 수 있습니다.

지침은 AI가 따르는 안내라 상황에 따라 건너뛸 수 있습니다. 린트·테스트처럼 매번 꼭 실행되어야 하는 검사는 hooks로 자동 실행하도록 설정할 수 있습니다.
