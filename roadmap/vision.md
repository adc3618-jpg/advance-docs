# 비전

> 대상 서비스: KFESS (https://flow.kgfinancial.co.kr/kfess/main/index.do)
> 범위: 프론트 / 스크래핑 서비스 / 잡서비스(API).

## 현재 상황

- 아키텍처가 프론트 / 스크래핑 서비스 / 잡서비스(API) 3개 축으로 나뉜 모놀리식 구조.
- 프론트엔드는 JSP + Java 1.8 기반 레거시 모놀리스. 신규 기능도 같은 스택 위에 얹는 구조라 변경 범위를 좁히기 어렵다.
- 배포가 무겁고 느리다 — 신규 개발 후 빠르게 배포해야 하는 상황에서도 배포 파이프라인이 이를 못 따라간다. 이것이 CI/CD 구축을 시작하는 직접적인 배경.
- 금융회사 특성상 일부 시스템이 폐쇄망(망분리) 안에 있어, DB 등 핵심 자원에 대한 접근이 물리적으로 제한된다. 클라우드로 전환하려면 이 경계를 넘나드는 방법이 별도로 필요하다.
- JSP + Java 1.8 조합은 채용 시장에서도, 최신 보안 패치·라이브러리 생태계 측면에서도 점점 더 유지비용이 커지는 스택이다.

## 목표

1. **프론트엔드 현대화** — 기존 JSP 화면을 API로 전환해 재활용하고, 화면은 **Next.js**(React 기반 프레임워크)로 새로 구성한다. JSP가 하던 서버사이드 렌더링을 Next.js의 SSR/SSG가 그대로 이어받으므로, SEO뿐 아니라 GEO(생성형 엔진 최적화 — AI 검색/답변 엔진 노출)까지 고려한 렌더링 전략을 프레임워크 선택만으로 확보한다. URL도 의미 있는 슬러그로 설계 단계부터 반영한다 (자세한 내용은 [`target-architecture.md`](target-architecture.md#프론트엔드-렌더링-전략-seogeo-고려) 참고). API로 전환하는 과정에서 Java 런타임도 1.8 → 11/17(LTS)로 단계적으로 올려, 보안 패치·라이브러리 생태계 문제를 함께 해소한다.
2. **클라우드 전환** — 프론트엔드를 먼저 클라우드로 이관하고, 이후 API/잡서비스도 단계적으로 옮긴다. 클라우드는 AWS를 사용하며, 배포 형태는 **컨테이너 + ECS**로 통일한다. 프론트(Next.js)·신규 API·스크래핑/잡서비스가 모두 같은 방식(이미지 빌드 → ECR → ECS 배포)으로 굴러가면 CI/CD·관측성·롤백 절차를 서비스마다 새로 만들지 않아도 된다.
3. **CI/CD 구축** — 배포 속도와 안정성을 동시에 확보한다. API 서비스부터 우선 구축한다.
4. **폐쇄망 극복** — 폐쇄망 DB 접근을 위한 DMZ API를 구축하고, 가능하다면 AWS Private Network(PrivateLink/Direct Connect 등)로 폐쇄망과 클라우드를 안전하게 연결한다.
5. **(장기) 마이크로프론트엔드로 확장** — 프론트엔드가 단일 서비스 분리를 넘어, 여러 마이크로서비스 화면이 모이는 슈퍼앱 구조로 진화한다.

이 다섯 가지는 순서대로 실행하는 별개의 프로젝트가 아니라, 서로를 전제로 하는 하나의 흐름이다. CI/CD가 없으면 Next.js 전환도, 폐쇄망 극복도 안전하게 반복 배포할 수 없고, DMZ API가 없으면 클라우드로 옮긴 프론트가 폐쇄망 DB를 참조하는 API를 호출할 방법이 없다.

## 왜 지금인가

- 국내 금융권도 2022~2023년 전자금융감독규정 개정 이후 망분리 규제가 단계적으로 완화되어, 상용 클라우드 이용 절차가 이전보다 명확해졌다. 규제가 클라우드 전환의 발목을 잡던 시기는 지나가는 중이다.
- 금융보안원의 「금융분야 상용 클라우드서비스 보안 관리 참고서」는 인터넷 구간(DMZ VPC)과 내부망(Internal VPC)을 분리하고 Transit Gateway로 연결하는 Multi-VPC 구조를 표준 패턴으로 제시한다. 우리가 만들려는 DMZ API 아키텍처와 방향이 같다. 다만 이 패턴에서 클라우드-폐쇄망 간 연결을 AWS PrivateLink/Direct Connect로 구성하는 부분은 국내 법규상 허용 여부를 법무팀 검토로 먼저 확인해야 한다(확인 필요) — 자세한 내용은 [`target-architecture.md`](target-architecture.md#목표-아키텍처)의 "AWS Private Network" 항목 참고.
- Netflix, Shopify 등 해외 사례는 "한 번에 다시 만들기"가 아니라 기존 시스템을 살려둔 채 점진적으로 이관하는 전략(스트랭글러 무화과 패턴)이 리스크를 가장 크게 줄인다는 것을 보여준다. 반대로 Amazon Prime Video 사례처럼 무조건 잘게 쪼개는 것이 항상 정답은 아니라는 교훈도 있다 — 자세한 내용은 [`target-architecture.md`](target-architecture.md) 참고.
- Capital One은 2020년 8개 온프레미스 데이터센터를 모두 폐쇄하고 AWS로 완전히 이관한, 금융회사 중 가장 잘 알려진 "올인 클라우드" 사례다. 재해복구 테스트 시간 70% 단축, 트랜잭션 오류 50% 감소, 개발 환경 구축 시간이 3개월에서 수 분으로 단축되는 결과를 얻었다 — [AWS 공식 사례 연구](https://aws.amazon.com/solutions/case-studies/capital-one-all-in-on-aws/). 우리와 마찬가지로 온프레미스·망분리 제약에서 출발했다는 점에서 규제 산업(금융)도 단계적으로는 완전한 클라우드 전환이 가능하다는 근거가 된다.

## 실사 관련 참고

이 저장소를 다루는 자동화 세션(예약된 루틴 포함)은 현재 실행 환경의 네트워크 정책상 `flow.kgfinancial.co.kr`에 직접 접속할 수 없다(egress 프록시가 해당 도메인 연결을 차단). 따라서 "현재 화면/동작 실사"는 브라우저 접근이 가능한 세션이나 담당자가 별도로 수행해야 하며, 이 문서의 개선 아이디어는 실제 화면 관찰이 아니라 목표·업계 사례 조사를 근거로 작성된 것이다. 실제 접속 결과(로딩 속도, 콘솔 에러, 페이지 소스 등)를 확인하면 이 절을 실사 기록으로 갱신한다.

## 타임라인

| 시기 | 목표 |
| --- | --- |
| 1단계 (현재~) | 모놀리식 구조를 유지한 채 신규 API를 지속 추가. 기존 JSP 프론트는 vanilla JS로 신규 API와 연동. API 서비스 대상 CI/CD 구축. 인증/세션 처리 방식 정리. |
| 1.5단계 | 폐쇄망 DB 접근용 DMZ API 설계·구축. 관측성(로깅/모니터링) 기반 마련. IaC 도입 착수. |
| 2단계 | 도메인/인프라를 AWS로 이관. Next.js 기반 프론트엔드 전환 및 ECS 배포. 프론트 CI/CD 구축. 스크래핑/잡서비스 컨테이너화 및 클라우드 이관. |
| 3단계 (장기) | 마이크로프론트엔드 기반 슈퍼앱 구조로 확장. 서비스별 자율 배포·자율 운영 체계 정착. |
