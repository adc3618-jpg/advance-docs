# 보안 체크리스트

> 구현을 마친 뒤 변경 사항을 점검하는 기준입니다. 예시이므로 실제 서비스의 정책에 맞게 바꿔서 씁니다.

## 입력 · 출력

- [ ] 모든 입력값을 서버에서 검증한다 (타입, 길이, 범위, 허용 값). 클라이언트 검증은 믿지 않는다.
- [ ] SQL은 바인딩 변수(`:param`, `#{}`)만 쓰고, 문자열을 이어 붙여 쿼리를 만들지 않는다.
- [ ] 사용자 입력을 화면에 출력할 때 이스케이프한다. `dangerouslySetInnerHTML`, `innerHTML`은 쓰지 않는다.
- [ ] 파일 업로드는 확장자 · MIME · 크기를 검증하고, 원본 파일명을 경로로 쓰지 않는다.

## 인증 · 인가

- [ ] 모든 API에 인증을 적용하고, 예외(공개 API)는 명시한다.
- [ ] 리소스 접근 시 소유자 · 권한을 서버에서 확인한다 (다른 사용자의 ID를 넣어도 조회되지 않아야 한다).
- [ ] 비밀번호는 평문으로 저장 · 로그 출력하지 않고, 단방향 해시로 저장한다.
- [ ] 세션 · 토큰은 만료 시간을 두고, 로그아웃 시 무효화한다.

## 데이터 보호

- [ ] 비밀키, 비밀번호, 토큰을 코드와 저장소에 넣지 않는다 (환경 변수 · 비밀 저장소 사용).
- [ ] 개인정보 · 계좌 정보는 로그에 남기지 않고, 화면에는 마스킹해서 보여 준다.
- [ ] 에러 응답에 스택 트레이스 · 쿼리 · 내부 경로를 넣지 않는다 (고정된 `code`만 내려준다).
- [ ] 삭제는 Soft Delete로 처리하고, 조회 쿼리에 `DELETED_AT IS NULL` 조건이 있는지 확인한다.

## 정산 · 금액

- [ ] 금액 · 수수료 계산은 서버에서 하고, 클라이언트가 보낸 금액은 신뢰하지 않는다.
- [ ] 금액 계산에 `BigDecimal`을 쓰고, 반올림 규칙을 명시한다.
- [ ] 중복 요청(재시도 · 더블 클릭)으로 같은 정산이 두 번 처리되지 않는지 확인한다.

## 의존성 · 설정

- [ ] 새로 추가한 라이브러리의 출처와 알려진 취약점을 확인한다.
- [ ] CORS · 쿠키 설정(`HttpOnly`, `Secure`, `SameSite`)을 필요한 범위로만 연다.
