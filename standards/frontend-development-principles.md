# 프론트엔드 개발 방향

> 백엔드/프론트엔드 책임 분리 원칙. Next.js 전환([`roadmap/target-architecture.md`](../roadmap/target-architecture.md))과
> 신규 API 설계 전반에 적용한다.

## 배경

레거시(JSP)는 화면과 로직이 서버에 묶여 있어, 문구 하나·포맷 하나를 바꾸려 해도 백엔드 배포가 필요했다.
API 중심 구조로 전환하면서 "무엇을 서버가 결정하고, 무엇을 클라이언트가 결정할지"를 명확히 하지 않으면
같은 문제가 API 계층에서 반복된다. 아래 네 원칙은 그 경계를 정한다.

## 원칙 1 — 백엔드는 원형 데이터를, 계산은 프론트가

백엔드는 가공되지 않은 최소 데이터만 내려주고, 표시를 위한 포맷팅·계산은 프론트엔드가 담당한다.

**나쁜 예**
```json
{ "price": "1,234,000원" }
```

**좋은 예**
```json
{ "amount": 1234000, "currency": "KRW" }
```
프론트에서는 `Intl.NumberFormat`으로 로케일/통화에 맞게 표시한다.

```js
new Intl.NumberFormat('ko-KR', { style: 'currency', currency: 'KRW' }).format(amount);
// "₩1,234,000"
```

**이유**
- 문자열로 내려오면 클라이언트가 다시 파싱해야 하는 역방향 작업이 생긴다 (정렬, 합계 계산, 단위 변환 등).
- 표시 형식(천 단위 구분자, 통화 기호, 소수점 자리수, 다국어 로케일)이 바뀌어도 백엔드 배포가 필요 없다.
- 같은 API를 웹/모바일/파트너사 등 여러 클라이언트가 쓸 때, 클라이언트마다 다른 표시 방식을 요구해도 API는 그대로 유지된다.

**적용 범위**: 금액뿐 아니라 날짜/시간(타임존 변환), 퍼센트, 단위(㎡ vs 평) 등 "표시를 위한 가공"이 필요한 모든 값에 동일하게 적용한다.
서버는 계산의 소스(합계, 세금, 할인 등 비즈니스 로직 결과값)까지는 책임지지만, 그 값을 "어떻게 보여줄지"는 책임지지 않는다.

## 원칙 2 — 사용자에게 보여줄 메시지는 프론트가 소유

API는 에러/상태를 기계가 읽을 수 있는 코드로만 응답하고, 그 코드를 사람이 읽을 문구로 바꾸는 일은 프론트가 한다.

**API 응답**
```json
{ "error": { "code": "NOT_FOUND" } }
```

**프론트 매핑**
```js
const MESSAGES = {
  NOT_FOUND: '찾을 수 없습니다.',
  UNAUTHORIZED: '로그인이 필요합니다.',
  VALIDATION_FAILED: '입력값을 다시 확인해 주세요.',
};

function toUserMessage(code) {
  return MESSAGES[code] ?? '알 수 없는 오류가 발생했습니다.';
}
```

**이유**
- 문구 수정(카피라이팅, 톤앤매너, 다국어 대응)이 백엔드 배포 없이 프론트 배포만으로 끝난다.
- 같은 에러 코드를 화면 맥락에 따라 다른 문구로 보여줄 수 있다 (예: 목록 화면과 상세 화면에서 `NOT_FOUND`의 안내 문구가 다를 수 있음).
- 코드가 안정적인 계약(contract)이 되어, 프론트가 `if (code === 'NOT_FOUND')` 같은 분기 처리(재시도 버튼 노출, 리다이렉트 등)를 문구와 독립적으로 할 수 있다.

**주의**: 코드 목록과 매핑 문구는 프론트 한 곳에서만 관리한다(마이크로프론트엔드 확장 시 공용 패키지로). 화면마다 매핑을 새로 만들면 원칙이 무색해진다.

## 원칙 3 — 입력값 검증은 프론트/백엔드 둘 다

형식 확인(필수값, 길이, 정규식 패턴 등 주요 검증)은 프론트와 백엔드 양쪽에서 각각 수행한다. 한쪽만 하지 않는다.

| 계층 | 목적 | 예시 |
| --- | --- | --- |
| 프론트 | 빠른 피드백(UX), 불필요한 API 호출 방지 | 이메일 형식, 필수 입력, 자릿수 제한을 입력 즉시 안내 |
| 백엔드 | 데이터 무결성 최종 방어선, 보안 | 동일 규칙을 서버에서도 재검증 — 프론트를 거치지 않은 요청(다른 클라이언트, 조작된 요청)도 막는다 |

**이유**
- 프론트 검증만 있으면: API를 직접 호출하는 경로(다른 클라이언트, 악의적 요청, 버그가 있는 신규 화면)에 대해 무방비 상태가 된다.
- 백엔드 검증만 있으면: 사용자가 실수를 입력 즉시 알 수 없어 UX가 나빠지고, API 왕복마다 서버 자원을 소모한다.
- 검증 규칙 자체(정규식, 최소/최대값 등)는 가능하면 한 군데(예: 공유 스키마/JSON Schema, zod 등)에 정의하고 프론트/백엔드가 같은 정의를 참조해, 두 계층의 규칙이 어긋나지 않게 한다.

## 원칙 4 — API에 값을 전달할 때도 가공된 값이 아닌 원형 값을 보낸다

원칙 1의 반대 방향이다. 입력 필드에 표시용으로 가공한 값(천 단위 콤마, 통화 기호, 마스킹된 형식 등)을
그대로 요청 payload에 담아 보내지 않는다. 화면에는 가공된 값을 보여주더라도, 서버로 보낼 때는 원형 값으로
되돌려 전달한다.

**나쁜 예**
```json
{ "amount": "1,234,000" }
```

**좋은 예**
```json
{ "amount": 1234000 }
```
입력창에는 사용자가 읽기 쉽도록 `1,234,000`을 표시하되, 상태값 자체는 숫자로 관리하고 전송 시점에 그 값을 그대로 보낸다.

```js
// 표시: 입력 이벤트마다 포맷된 문자열을 보여주되
const displayValue = new Intl.NumberFormat('ko-KR').format(amount);
// 전송: 상태로 들고 있는 원형 숫자를 그대로 전달
await api.post('/orders', { amount });
```

**이유**
- 서버가 콤마·통화기호·마스킹 형식을 다시 파싱해야 한다면, 원칙 1로 없앤 "포맷 파싱 책임"이 요청 방향에서 되살아난다.
- 포맷은 로케일/화면마다 다를 수 있어(`1,234,000` vs `1.234.000`), 서버가 이를 모두 이해하도록 만들면 클라이언트별 포맷 방언에 서버가 결합된다.
- 원형 값으로 보내면 백엔드 검증(원칙 3)도 타입 그대로 단순하게 적용할 수 있다 (문자열 파싱 실패, 콤마 위치 오류 같은 불필요한 예외 케이스가 사라짐).

**적용 범위**: 금액뿐 아니라 전화번호(하이픈), 날짜(로케일별 표기), 카드번호(4자리 구분 공백) 등 "입력 편의를 위해 화면에서만 가공하는" 모든 값에 적용한다.
표시용 포맷팅과 상태값을 분리하는 것이 핵심 — 상태는 항상 원형으로 유지하고, 포맷은 렌더링 시점에만 적용한다.

## 네 원칙을 관통하는 기준

> **서버는 "정답 데이터와 규칙"을 책임지고, 화면에 어떻게 보여줄지는 클라이언트가 책임진다.**

이 기준으로 애매한 경우를 판단한다:
- "이 값을 다른 클라이언트(모바일, 파트너 API)가 다른 방식으로 보여줘야 할 수 있는가?" → 그렇다면 가공하지 말고 원형으로 내려준다.
- "이 메시지/문구가 마케팅·정책·다국어 이유로 자주 바뀌는가?" → 그렇다면 코드화하고 프론트가 매핑한다.
- "이 검증이 뚫리면 데이터가 깨지거나 보안 문제가 되는가?" → 그렇다면 반드시 백엔드에도 동일 규칙을 둔다.
- "이 값은 화면에 보여주기 위한 가공인가, 서버로 보내기 위한 값인가?" → 표시용 포맷과 전송용 원형 값은 항상 분리해서 관리한다.

## 코드 리뷰 체크리스트

- [ ] API 응답에 화면 표시용으로 이미 포맷된 문자열(통화 기호, 천단위 콤마, "n일 전" 같은 상대 시간 등)이 섞여 있지 않은가?
- [ ] 에러/상태 응답이 고정된 `code`로 내려오고, 사용자 문구는 프론트 매핑 테이블에만 있는가?
- [ ] 신규 입력 필드에 대해 프론트 검증과 백엔드 검증이 모두 추가되었는가? 두 규칙이 같은 소스(스키마)에서 나왔는가?
- [ ] API 요청 payload에 콤마·통화기호·마스킹 등 화면 표시용으로 가공된 값이 그대로 담겨 있지 않은가?
